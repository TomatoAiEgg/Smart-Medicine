# 智能药房 SaaS 后台全局 UI 基线改造设计

日期：2026-08-15

## 背景

当前前端已经接入 `frontend/admin-web/DESIGN.md` 和 Impeccable，但实际界面仍存在明显不统一问题。经检查，主要证据如下：

- `frontend/admin-web/src/styles/base.css` 体量约四千行，包含多轮旧 JSP/EasyUI 风格、现代化皮肤、Product UI refresh、cloud console 等历史样式覆盖。
- 公共壳层已经拆到 `frontend/admin-web/src/app/AppLayout.vue` 和 `src/styles/admin-shell.css`，但最终视觉仍受 `base.css` 后续覆盖和各页面 scoped 样式影响。
- 约 50 个业务页面各自维护局部样式，筛选区、表格、按钮、状态标签、页面标题、弹窗/抽屉的密度和层级不一致。
- 老项目的信息架构和父子菜单布局可作为结构参考，但其视觉风格偏旧，不应直接复制。

本次目标是先做“全局壳层和基础组件规范”的第一阶段改造，不直接展开所有父级菜单的逐页重做。

## 目标

建立一套可落地的后台 UI 基线，让后续页面改造有统一标准：

- 保留老系统正确的信息架构：左侧父子菜单、顶部租户/用户区、页签、多页面工作区。
- 统一全局壳层：顶部栏、侧边栏、路由页签、页面标题区、工作区背景和间距。
- 统一基础组件视觉：筛选区、表格、按钮、状态标签、分页、空状态、加载状态、弹窗/抽屉。
- 清理公共 CSS 覆盖链，减少历史样式互相覆盖造成的不可预测结果。
- 选 2 到 3 个代表页面验证基线，形成后续父级菜单分阶段迁移的样板。

## 非目标

- 不修改业务逻辑、接口、权限、路由守卫、登录流程、数据模型。
- 不一次性重做所有业务页面。
- 不引入新的 UI 组件库替换 TDesign Vue Next。
- 不复制第三方产品品牌、商标、专有图片或营销文案。
- 不提交视觉讨论产生的 `.superpowers/` 临时文件。

## 设计方向

视觉方向以 `frontend/admin-web/DESIGN.md` 为准：克制、密集、清晰、偏运营工作台，而不是营销型后台。

关键规则：

- 主色继续使用 `#0052D9`，只用于主操作、激活导航、链接、焦点和选中态。
- 工作区使用浅灰背景，业务面板使用白色和 1px 边框。
- 保持低圆角：控件约 3px，面板不超过 6px 到 8px。
- 避免装饰性渐变、玻璃拟态、大面积阴影、过多卡片和浮夸首屏。
- 页面优先服务“找记录、筛选、比较、查看详情、执行受控操作”。

## 架构与边界

### 公共壳层

范围：

- `AppLayout.vue`
- `admin-shell.css`
- `admin-tokens.css`
- `base.css` 中影响后台壳层和基础组件的历史覆盖规则

公共壳层应稳定提供：

- 左侧父子菜单，父级和子级层级清晰，激活态明确。
- 顶部租户、用户、退出和必要的系统操作。
- 路由页签，不因文本长度或关闭按钮导致布局跳动。
- 页面标题区，统一展示标题、副标题、刷新或主要动作。
- 移动端侧栏抽屉和遮罩，不产生页面级横向溢出。

### 基础组件基线

先以 CSS 和已有 TDesign 组件能力统一以下模式：

- 筛选工具栏：紧凑排列、可换行、查询/重置/导出与筛选项保持视觉关联。
- 表格容器：统一表头、行高、边框、滚动、空状态、加载状态、批量操作位置。
- 按钮：主按钮唯一突出，次按钮中性，危险按钮语义明确。
- 状态标签：低饱和语义色，文字必须说明状态，不能只靠颜色。
- 抽屉/弹窗：标题、关闭、底部操作、禁用/提交中状态保持一致。

### 代表页面

第一阶段只选择少量代表页面验证，而不是全量铺开。候选应覆盖：

- 一个列表型页面：验证筛选区、表格、分页、行操作。
- 一个详情/编辑型页面：验证抽屉或弹窗、表单、只读状态。
- 一个工作台或配置型页面：验证页面标题、区域组织、空状态或权限状态。

具体页面在实施计划中依据现有路由和代码复杂度确定。

## 数据与流程

本次不改变数据流。所有页面继续使用现有：

- Vue 3 + Vite + TypeScript
- TDesign Vue Next
- 现有路由、鉴权、权限、会话和 API 调用

UI 改造只允许改变结构性样式、组件排布和展示层，不改变提交参数、接口字段、权限判断或业务状态流转。

## 风险

- `base.css` 历史覆盖较多，删除或调整规则可能影响未纳入代表页面的旧页面。
- scoped 样式分散在多个业务页，公共基线可能被局部样式覆盖。
- 一次性清理过大容易引入视觉回退或交互断裂。

控制方式：

- 先保留业务页面结构，优先收敛公共壳层和基础组件类名。
- 分阶段清理 `base.css`，避免一次性删除无法确认影响的规则。
- 每轮只选代表页面验证，确认后再扩展到其它父级菜单。

## 回滚路径

- 所有改造以独立提交落地，必要时可通过 Git 回退本阶段提交。
- 不提交构建产物和临时预览文件。
- 不修改接口和数据库，因此回滚只涉及前端资源重新构建和部署。

## 验证计划

实施阶段必须完成：

- 运行 `npm run build` 验证构建。
- 使用 Impeccable 对触达页面或路径执行 audit/polish。
- 人工检查至少桌面和窄屏两种视口，重点看导航、筛选区、表格横向滚动、按钮换行、文字溢出、弹窗/抽屉。
- 验证代表页面的关键点击路径：进入页面、查询/重置、打开详情或编辑、关闭弹层、刷新或返回。

## 验收标准

- 全局壳层视觉统一，父子菜单、顶部栏、页签、页面标题区不再出现明显风格割裂。
- 代表页面的筛选区、表格、按钮、状态标签和弹窗/抽屉符合 `DESIGN.md`。
- 页面不出现明显文本重叠、按钮挤压、组件错位、页面级横向溢出。
- 构建通过，Impeccable 审查结果无新增高优先级 UI 问题。
- 无业务逻辑、接口、权限和数据流变更。

## 用户确认结果

用户已确认采用方案 2：建立统一后台 UI 基线，再套到公共壳层和代表页面。

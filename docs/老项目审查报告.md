# 老项目审查报告

## 1. 审查结论

本次审查确认，老系统不是单一后台项目，而是由内部管理后台、外部接口网关、异步消费服务和共享业务库共同组成的一套智能药房业务系统：

- `D:\workproject\chengyou\1\zhyfsupport`：内部管理后台，承担菜单、用户、机构、参数、药品、订单、物流、煎煮、短信、标签、报表、运维等管理能力。
- `D:\workproject\chengyou\1\zhyf-api`：外部接口与异步处理项目，包含 `zhyf-gateway`、`zhyf-async`、`zhyf-common` 三个模块，承担机构接口接入、签名校验、白名单校验、订单创建、物流接口、PDA/MES 接口、状态回调和 MQ 异步任务。
- `C:\Users\13372\Desktop\backup20250520.sql`：老系统库表结构来源。本次只读取库表结构和菜单配置，不纳入历史业务数据。

因此，新系统重构不能只做一个前端壳，也不能只恢复少量核心页面。验收边界应当覆盖老后台 11 个一级菜单、68 个二级菜单对应的业务能力，并把 `zhyf-api` 中的外部协议、鉴权规则、异步消费和回调链路纳入后端重构范围。

当前新项目已有技术方向和部分核心链路雏形，但功能覆盖仍明显不足。尤其是前端菜单、后台管理 CRUD、药品目录、短信、标签、完整报表、接口权限、白名单、外部 API 兼容、MQ 消费可观测等能力，需要按老系统业务重新补齐。

## 3. 老系统整体架构

### 3.1 `zhyfsupport` 内部后台

`zhyfsupport` 是传统 Spring MVC + JSP + jQuery/EasyUI/Bootstrap 后台。主布局在 `src/main/webapp/WEB-INF/jsp/index.jsp`，通过数据库菜单加载左侧导航，再以 tab 方式打开 JSP 页面。

主要特点：

- 菜单配置来自 `tb_menu`，菜单查询逻辑在 `src/main/resources/mybatis/Menu.xml`。
- 页面集中在 `src/main/webapp/WEB-INF/jsp/**`。
- 业务控制器集中在 `src/main/java/com/sy/controller/**`。
- 数据访问大量依赖 MyBatis XML。
- 业务入口以 `.html` 路由形式暴露，实质是后台控制器返回 JSP 或 JSON。

### 3.2 `zhyf-api` 外部接口与异步服务

`zhyf-api` 是 Spring Boot 1.5 + Spring Cloud Edgware 时代的多模块项目：

| 模块 | 职责 |
| --- | --- |
| `zhyf-common` | 公共实体、枚举、MQ 常量、工具类、接口 DTO |
| `zhyf-gateway` | 机构外部接口、PDA/MES/物流接口、鉴权、入库、消息生产 |
| `zhyf-async` | ActiveMQ 消费者、异步校验、推送、短信、状态回调 |

它不是简单的网关转发层，而是直接参与业务写入和流程推进。新系统重构时应把它升级为“外部协议适配层 + 应用服务 + MQ 异步任务”的组合，不能丢失原有机构对接协议。

### 3.3 共享业务库

`backup20250520.sql` 中与本系统最相关的是 `zhy_online_db`，共识别 65 张业务表。核心表围绕订单、处方、处方明细、机构、接口权限、白名单、药品、物流、煎煮、短信、标签、MQ 消息、日志、系统配置展开。

新系统不应照搬老库命名和字段风格，但必须把这些表对应的业务对象、状态字段、外部编号、幂等字段、流程字段、日志字段纳入新模型设计。

## 5. 内部后台业务梳理

### 5.1 系统管理

系统管理负责后台用户、角色、菜单三类基础权限能力。老系统通过 `tb_user`、`tb_role`、`tb_menu` 维护后台身份和菜单授权。

重构要求：

- 新系统应建立统一后台账号、角色、菜单、按钮/接口权限模型。
- 前端菜单不应硬编码成少量页面，应支持从后端返回菜单树。
- 菜单编码应与路由、权限标识、审计日志关联。
- 老菜单可以作为迁移种子数据，但权限粒度要升级到现代 RBAC。

### 5.2 参数管理

参数管理包含字典、系统配置、煎煮中心、工号管理。它是订单、物流、煎煮、报表等模块的基础配置来源。

相关表包括：

- `zhyf_dict`
- `zhyf_system_config`
- `zhyf_decoct_center`
- `zhyf_oper_user`

重构要求：

- 字典和系统参数要有类型、编码、启停状态、排序、租户/机构作用域。
- 工号要与实际作业节点绑定，支撑审核、调剂、复核、煎煮、物流等绩效统计。
- 煎煮中心配置不能只做静态表单，需要参与订单分配、设备绑定和外部推送规则。

### 5.3 机构管理

机构管理是外部接口接入的核心。老系统的机构、接口列表、接口权限、IP 白名单共同构成接入鉴权体系。

相关表包括：

- `zhyf_institutions`
- `zhyf_api_info`
- `zhyf_api_permission`
- `zhyf_white_ip`

老 `zhyf-api` 的调用校验包含：

- 机构是否存在且启用。
- 调用方法是否在接口列表中。
- 机构是否拥有该接口权限。
- 来源 IP 是否满足白名单要求。
- 时间戳是否在允许窗口内。
- 请求签名是否匹配。

重构要求：

- 保留旧机构调用协议的兼容层，避免医院/机构侧一次性改造。
- 新增应用凭证、接口授权、白名单、调用日志、限流、幂等记录。
- 把鉴权结果写入访问日志，便于排查机构接入问题。

### 5.4 订单管理

订单管理是老系统最大的业务域，覆盖处方列表、审核、调剂、复核、地址修改、处方修改、订单操作、处方重打、仓库、拦截、流程推进、签收等 14 个二级菜单。

核心表包括：

- `zhyf_order`
- `zhyf_prescription`
- `zhyf_prescription_details`
- `zhyf_prescription_drugusage_mapping`
- `zhyf_fillpush_prescriptions_intercept`

老系统核心业务对象：

- 订单：机构、外部单号、订单状态、物流状态、支付/费用、收件信息、创建来源。
- 处方：处方编号、患者信息、医生信息、用药方式、煎煮要求、审核/调剂/复核/煎煮流程状态。
- 处方明细：药材、剂量、单位、脚注、匹配状态。
- 流程记录：订单从接单、审核、调剂、复核、煎煮、打包、发货、签收的节点痕迹。

重构要求：

- 订单域必须成为新系统核心域模型，不能把所有字段平铺到一个大表后直接 CRUD。
- 流程状态要拆成订单状态、处方状态、生产作业状态、物流状态、异常状态。
- 审核、调剂、复核、煎煮、物流等动作必须可追踪、可回退、可补偿。
- 订单修改、处方修改、地址修改要有操作审计。
- 处方重打、流程推进、拦截配置属于高风险管理动作，应增加权限和二次确认。

### 5.5 物流管理

物流管理覆盖规则配置、地址费用、发货查询、物流轨迹、打单、合并、未签收跟进。

相关表包括：

- `zhyf_logis_special`
- `zhyf_logis_companycost_addr`
- `zhyf_logis_info`
- `zhyf_logis_region_config`
- `zhyf_logistics_additive`
- `zhyf_order_merge`

重构要求：

- 建立物流服务域，区分发货单、运单、轨迹、费用规则、合并包裹。
- 面单打印应抽象为物流供应商适配器。
- 未签收跟进要支持筛选、处理记录、提醒和关闭状态。
- 物流回调要进入消息/事件模型，避免直接修改核心订单状态后不可追踪。

### 5.6 煎煮管理

煎煮管理覆盖设备、处方设备绑定、打码机、加水桶、云打印。

相关表包括：

- `zhyf_equipment_manage`
- `zhyf_prescription_bind_info`
- `zhyf_pda_dmj_relation`
- `zhyf_waterpail_info`
- `zhyf_bq_print_record`
- `zhyf_jyj_state`
- `zhyf_jyj_work`

重构要求：

- 把煎煮设备、PDA、打码机、加水桶视为设备资源模型。
- 处方绑定设备应具备幂等、冲突检测、解绑/重绑审计。
- 设备回调和人工操作都要进入统一作业事件表。
- 云打印记录要支撑重打、失败重试、打印机状态排查。

### 5.7 标签管理

标签管理包含处方标签设置和处方标签打印。

相关表包括：

- `zhyf_decocting_lableset`
- `zhyf_bq_print_record`

重构要求：

- 标签模板应独立建模，支持机构、煎煮中心、处方类型等作用域。
- 标签打印要沉淀打印任务、打印结果、重打记录。
- 前端应提供模板预览和打印历史查询。

### 5.8 短信管理

短信管理包含模板、单发短信、短信列表查询。

相关表包括：

- `zhyf_sms_moudle`
- `zhyf_sms`

重构要求：

- 短信模板与发送记录要独立管理。
- 发送动作应走消息队列，避免页面操作阻塞。
- 短信状态、失败原因、重试次数、关联订单应可查询。
- 单发短信必须纳入权限和审计。

### 5.9 药品管理

药品管理包含药品目录、药品索引、操作日志、导入、区域管理。

相关表包括：

- `zhyf_herbs`
- `zhyf_herbs_index`
- `zhyf_herbs_area`
- `zhyf_important_oper_log`

重构要求：

- 药品主数据要区分标准药品、机构药品、索引映射、区域库存/区域配置。
- 药品导入要做成异步任务，包含导入预检、错误明细、导入结果。
- 药品索引变更是影响处方匹配的高风险动作，必须保留操作日志。
- 处方入库后的药品匹配过程要可解释，便于排查机构药名不一致问题。

### 5.10 报表管理

报表管理是老后台的重要能力，不是一个概览接口可以替代。老系统至少包含处方量、机构处方量、审核员/调剂员/复核员/煎煮员/物流员绩效、对账、药材用量等 16 个报表入口。

重构要求：

- 报表服务要从一开始设计统计维度：时间、机构、人员、流程节点、药材、订单状态。
- 明细报表和汇总报表要分开建模。
- 导出任务应异步化，支持大数据量导出和下载记录。
- 绩效报表依赖作业人员和流程事件，不能只靠订单当前状态反推。

### 5.11 维护管理

维护管理包含订单流程查询、异常日志、MQ 消息、问题件登记。

相关表包括：

- `zhyf_log_exception`
- `zhyf_log_info`
- `zhyf_mq_message`
- `zhyf_order_problem_registration`

其中 `zhyf_order_problem_registration` 未在本次 SQL 转储中识别到建表语句，但老后台 Mapper 和实体存在该业务对象，应在新系统中补齐为问题件管理能力。

重构要求：

- 订单流程查询要基于事件和状态流转记录。
- 异常日志要关联订单、机构、接口、消息、请求链路。
- MQ 消息要能查询生产、消费、失败、重试、死信、回调结果。
- 问题件登记要支持登记原因、处理方案、金额、备注、处理状态和操作记录。

## 6. 外部接口与异步业务梳理

### 6.1 外部接口入口

`zhyf-gateway` 暴露的主要接口包括：

| 控制器 | 主要接口 | 业务说明 |
| --- | --- | --- |
| `OrderApiController` | `/healthCheck`、`/createOrder`、`/cancelOrder`、`/queryOrder`、`/updateOrderAddress`、`/getOrderId` | 机构订单接入、取消、查询、地址修改 |
| `LogisticsController` | `/logistics/createLogisticsOrder`、`/cancelLogisticsOrder`、`/queryBillPrintInfo`、`/printWaybills`、`/queryLogisticsCost`、`/queryEmsPdfFile`、`/notify`、`/emsNotify`、`/queryLogisticsInfo` | 物流下单、取消、打单、费用、轨迹、回调 |
| `PDAController` | `/pdaUserLogin`、`/pdaGetDecoctEquip`、`/pdaBindPrescription`、`/pdaOpDecoctStatus`、`/pdaGetCanOpRecipeList`、`/pdaLabelPrintInit`、`/pdaRecipeQuery`、`/pdaLabelPrint`、`/pdaLogisticsOutbound` | PDA 登录、设备、绑定、打印、出库 |
| `MachineApiController` | `/getWaterByPailNo`、`/waterEndNotice`、`/getRecipeInfoById`、`/recipeBoilInfoCallback`、`/reviewFinishPushRecipe`、`/decoctingStatusNotice` | 煎煮设备/MES 回调 |
| `SmartCloudOrderApiController` | `/zhy/healthCheck`、`/zhy/syncHospitalRecipel`、`/zhy/modHospitalRecipel`、`/zhy/cancelRecipel`、`/zhy/recipeStatusCallback` | 智慧云处方同步协议 |
| `SzlgzxyyOrderApiController` | `/szlgzx/healthCheck`、`/szlgzx/zhyfCreateOrder`、`/szlgzx/zhyfCancelOrder` | 特定机构定制协议 |

重构要求：

- 这些接口应作为兼容协议保留，内部再转换为新系统应用命令。
- 特定机构协议不能污染核心订单模型，应放在 adapter 层。
- 健康检查、验签失败、权限失败、业务失败的响应码要兼容老调用方。

### 6.2 接入鉴权

老接口鉴权主要由机构、接口权限、白名单、时间戳、签名共同完成。

关键规则：

- 根据机构接入身份查找机构。
- 校验接口方法是否存在且授权给该机构。
- 校验来源 IP 是否满足白名单。
- 校验调用时间是否超过允许窗口。
- 按老规则计算请求签名并比对。

重构要求：

- 新系统可以使用 Spring Security 统一认证框架，但外部机构协议层必须兼容老签名。
- 鉴权失败应记录机构、接口、失败原因、请求时间、来源地址。
- 对外接口要支持幂等键、请求流水号、重复提交识别。

### 6.3 创建订单链路

老 `createOrder` 链路大致为：

1. 解析机构提交的 JSON。
2. 校验请求头、机构、接口权限、白名单和签名。
3. 使用 Redis 做短期重复提交控制。
4. 检查外部处方/订单是否重复。
5. 写入订单、处方、处方明细。
6. 记录物流或接单日志。
7. 事务提交后发送 `createOrderSuccess.service.queue` 消息。
8. 异步执行药品匹配、处方校验、楼层/MES 建议、审核平台推送等后续动作。

重构要求：

- 同步接口只负责接单和返回明确结果，后续长耗时任务进入 RocketMQ。
- 使用 Outbox 保证数据库事务和消息发送一致。
- 每个外部订单要有幂等记录和接入日志。
- 药品匹配、处方校验、外部推送失败不能丢失，要可查询、可重试、可补偿。

### 6.4 MQ 异步链路

老系统 ActiveMQ 队列包括：

- `createOrderSuccess.service.queue`
- `reviewFinishPushRecipe.service.queue`
- `sendMsgMessageMQ.service.queue`
- `orderInfoValidationMQ.service.queue`
- `threeAudit.service.queue`
- `orderStatusChange.service.queue`

主要消费者职责：

| 消费任务 | 业务职责 |
| --- | --- |
| 创建订单成功消费 | 药品匹配、处方校验、生成楼层/MES 建议、审核平台推送 |
| 复核完成推送 | 将处方推送到煎煮/设备侧 |
| 订单状态变更 | 根据状态向机构回调订单/处方状态 |
| 订单信息校验 | 后台修改后触发重新校验 |
| 短信发送 | 异步发送短信 |
| 三方审核 | 兼容旧三方审核链路 |

重构要求：

- ActiveMQ 升级为 RocketMQ 后，应保留业务事件名称和语义映射。
- 消费日志、重试、死信、失败原因要进入运维后台。
- 回调机构应独立为 callback 任务，支持重试和人工补偿。
- 消费幂等必须按业务主键和事件类型控制，不能只依赖消息 ID。

### 6.5 PDA、MES、物流与定制机构协议

老系统不仅接收医院处方，还对接 PDA、煎煮设备、物流系统和特定机构协议。

重构要求：

- PDA 接口要覆盖登录、可操作处方、设备绑定、标签打印、物流出库。
- MES/煎煮接口要覆盖取水、完成通知、处方信息查询、煎煮状态回调。
- 物流接口要覆盖下单、取消、面单、费用、轨迹和回调。
- 特定机构协议要用独立 adapter，避免核心服务出现大量定制分支。

## 8. 当前新项目差距

### 8.1 前端差距

当前新前端只有少量视图入口，例如工作台、门户查单、处方列表、审核、调剂、复核、订单流程、物流发货、煎煮作业、集成任务、运维审计、报表统计。它还没有覆盖老后台 68 个二级菜单。

主要差距：

- 系统管理、参数管理、机构管理只有部分概念，没有完整页面。
- 药品管理、短信管理、标签管理基本缺失。
- 报表只做了概览，未恢复 16 个报表入口。
- 订单管理缺少地址修改、处方修改、订单操作、处方重打、仓库、拦截、流程推进、签收等页面。
- 物流管理缺少规则、费用、轨迹、打单、合并、未签收跟进的完整闭环。
- 前端菜单需要改成真实业务菜单树，而不是抽象工作台式导航。

### 8.2 后端差距

当前新后端已有订单、流程、物流、煎煮、运维、报表等部分服务雏形，但距离老系统功能完整恢复仍有较大差距。

主要差距：

- 外部接口协议未完整覆盖 `zhyf-api` 所有入口。
- 机构鉴权、接口权限、白名单、老签名兼容需要完整落地。
- 药品主数据、药品索引、导入任务、操作日志缺失。
- 短信模板、短信发送、短信记录缺失。
- 标签模板、标签打印、打印记录缺失。
- 完整报表体系缺失。
- 问题件登记、MQ 消息查询、异常日志和流程追踪需要与新消息体系打通。
- 订单修改、地址修改、处方修改、重打、手工推进等高风险后台操作需要补齐。

### 8.3 数据模型差距

当前新库表设计已覆盖部分核心链路，但还不足以承接老系统完整业务。

需要补齐：

- 后台用户、角色、菜单、权限。
- 字典、系统参数、煎煮中心、工号。
- 机构接口、接口权限、白名单、访问日志。
- 药品目录、药品索引、区域、导入任务、操作日志。
- 标签模板、打印任务。
- 短信模板、短信任务。
- 物流费用规则、合并发货、未签收跟进。
- 问题件登记。
- 报表统计所需的流程事件和作业绩效明细。

## 9. 重构后的业务边界

新系统应按以下边界拆分能力：

| 能力域 | 目标服务/模块 | 重构重点 |
| --- | --- | --- |
| 接入网关 | `gateway` / integration adapter | 兼容老协议、鉴权、白名单、限流、接入日志 |
| 订单处方 | `order-service` | 订单、处方、处方明细、修改、取消、查询、幂等 |
| 流程作业 | `workflow-service` | 审核、调剂、复核、流程推进、绩效事件 |
| 煎煮设备 | `decoction-service` | 设备、PDA、MES、绑定、打码、加水桶、云打印 |
| 物流 | `logistics-service` | 发货、运单、轨迹、费用、合并、签收 |
| 药品 | `drug-service` | 药品目录、索引、区域、导入、匹配 |
| 机构接入 | `institution-service` | 机构、接口、授权、白名单、协议配置 |
| 系统权限 | `admin-service` | 用户、角色、菜单、字典、参数、工号 |
| 消息回调 | `message-service` / `ops-service` | Outbox、RocketMQ、消费日志、死信、回调任务 |
| 短信 | `sms-service` 或消息模块子域 | 模板、发送、记录、重试 |
| 标签打印 | `print-service` 或煎煮子域 | 模板、打印任务、重打、记录 |
| 报表 | `report-service` | 处方量、绩效、对账、药材用量、导出 |
| 运维审计 | `ops-service` | 异常日志、访问日志、订单轨迹、MQ 查询、问题件 |

如果为了简历和学习价值，服务可以先按模块化单体或少量微服务落地，但代码结构必须体现这些边界。否则后续拆服务时会再次陷入老系统式大控制器和大表。

## 11. 验收口径

后续重构验收不应只看页面是否好看，而应按业务能力验收：

- 前端菜单是否覆盖老后台 11 个一级菜单、68 个二级菜单。
- 每个菜单是否有真实路由、列表、查询条件、详情或编辑动作。
- 外部机构是否能按老协议完成健康检查、创建订单、取消、查询、地址修改。
- 鉴权、白名单、接口权限、签名失败是否有明确错误和日志。
- 创建订单后是否能异步触发药品匹配、校验、流程推进和回调任务。
- 审核、调剂、复核、煎煮、发货、签收是否能形成完整流程轨迹。
- MQ、回调、异常、问题件是否能在运维后台查询和补偿。
- 报表是否至少恢复老系统的统计入口和导出能力。
- 数据库设计是否能解释老系统核心表和字段，不遗漏关键业务对象。

## 12. 最终判断

本次审查后，可以明确当前重构方向需要从“前端界面重做”升级为“老系统业务能力重构”。技术栈已经可以确定，下一步重点不是继续调样式，而是按照本报告把老项目业务拆成可实现的模块、接口、页面和库表迁移任务。

建议后续以本报告作为业务基线，再继续完善：

- `docs/功能方案/前端功能方案.md`
- `docs/功能方案/后端功能方案.md`
- `docs/数据设计/数据库重构设计.md`
- `docs/03_架构设计/重构方案.md`

其中前端方案应直接引用 68 个菜单作为路由恢复清单；后端方案应把 `zhyfsupport` 与 `zhyf-api` 合并视为一个系统的两部分，而不是两个无关项目。

本轮在原业务审查基础上，对老项目前端源码做了全量页面级静态审查。页面口径如下：

| 范围 | 数量 | 说明 |

## 14. 全局 UI 与布局

### 14.1 登录页

`login.jsp` 是独立全屏登录页，不使用后台主框架：

- 背景使用铺满视口的 `bgimga.jpg`，背景色为深蓝灰 `#1B3142`。
- 登录区固定约 380px 宽，位于页面右侧，使用半透明白色背景和 15px 圆角。
- 表单包含用户名、密码和验证码；按钮为 78x36px 的钢蓝色矩形按钮。
- 页面依赖大量绝对位置、固定高度和 `margin-left: 70%`，适配目标明显是固定桌面分辨率，窄屏会产生偏移或溢出。

### 14.2 后台主框架

`index.jsp` 是唯一直接使用 EasyUI 布局组件的核心页面。其结构为：

```text
EasyUI Layout
├─ North：48px 顶栏
│  ├─ 系统名称“良益堂煎药管理系统”
│  └─ 当前用户、修改密码、退出等操作
├─ West：200px 左侧导航
│  └─ EasyUI Accordion 一级菜单 + 二级菜单
├─ Center：EasyUI Tabs
│  ├─ 默认首页
│  └─ 每个业务菜单以 iframe 打开为一个标签页
└─ South：25px 底栏
```

主框架视觉参数：

| 元素 | 老系统规则 |
| --- | --- |
| 顶栏 | `#242f42`，48px 高，系统名 22px 白字 |
| 左栏 | `#324157`，200px 宽，深色 Accordion |
| 菜单项 | 32px 高，白字；悬停使用 `#20a0ff` / `#2b7dbc` |
| 内容区 | 多标签页，每页是独立 iframe，宽高 100% |
| 底栏 | 25px 高，使用重复背景图 |

这套结构的业务价值是同时保留多个工作页面并快速切换。新前端可以用 Vue Router + 可关闭标签缓存替代 iframe，但应保留“左侧分组菜单 + 顶部页签 + 中央工作区”的操作习惯。

### 14.3 通用业务页面骨架

绝大多数业务页不是 EasyUI 页面，而是 Bootstrap 与自定义 CSS 组合。119 个 JSP 中，105 个引用 Bootstrap，104 个使用 `padding_10`，100 个使用 `head-title`，71 个使用 `main_table`，60 个使用 `search_div`。

典型列表页结构固定为：

```text
padding_10
├─ head-title
│  ├─ h1 页面名称
│  └─ 右侧操作按钮：新增 / 导入 / 导出 / 打印
└─ span12
   └─ form
      └─ portlet-body > tabbable > tab-content
         ├─ search_div：横向换行的筛选项与查询按钮
         ├─ main_table：表头、数据行、行内操作
         └─ page_and_btn：左侧统计文字 + 右侧分页
```

典型编辑页结构为 `accordion2` 折叠容器或纵向表单，通常被列表页通过 Bootstrap Modal + iframe 打开。保存成功后由子 iframe 调用 `parent` 关闭弹窗并刷新列表。

## 17. 打印、弹窗与交互模式

### 17.1 打印

老系统深度依赖 Lodop，而不是浏览器原生打印：

- 调剂打印和处方重打使用 A5 横向/纵向纸张、二维码、班次和药品明细。
- 物流发货和物流打单同时生成条码、物流二维码、订单二维码和面单内容。
- 煎药标签按 600x600、600x400、550x400 等自定义尺寸定位文字和 HTML。

新前端不能仅做“打印按钮”。需要独立的打印模板模型、预览、打印机选择、任务状态、失败重试和历史记录，并验证实际纸张尺寸。

### 17.2 弹窗

老系统主要有两种弹窗：

- 列表页内 Bootstrap Modal，适合合单、未签收备注、处方修改等短操作。
- Modal 内 iframe，适合新增/编辑独立 JSP，子页面通过 `parent` 控制关闭和刷新。

Vue 重构应改为组件化 Dialog/Drawer，避免 iframe 和跨窗口 DOM 调用；但“保存后关闭并刷新原列表”的业务反馈必须保留。

### 17.3 筛选与分页

筛选区使用无卡片的横向 `ul.search_div`，项目较多时自然换行；按钮紧跟筛选项。分页在表格下方，左侧显示统计信息，右侧为 30px 方形页码。新前端应继续采用紧凑筛选工具栏，桌面端优先横向排布，小屏再折叠为抽屉或多行表单。

## 18. UI 与前端工程问题

| 问题 | 证据 | 对重构的影响 |
| --- | --- | --- |
| iframe 标签页耦合 | 主框架所有业务菜单通过 iframe 打开 | 路由状态、权限、刷新和跨页通信难维护 |
| 固定像素严重 | 1220 处固定宽度规则 | 宽屏浪费空间，窄屏溢出 |
| 内联样式多 | 857 处 `style=`/页面样式 | 主题和一致性难统一 |
| 语义与无障碍弱 | 87 个输入页没有语义化 label | 键盘、读屏和表单错误关联不足 |
| DOM id 冲突 | 12 个页面有重复 id | 事件绑定和取值存在不确定性 |
| HTML 标准陈旧 | 113 页使用 HTML4 Transitional | 不适合直接迁移到现代组件体系 |
| 表格承担过多布局 | 161 张 HTML 表格 | 详情和表单在响应式环境难适配 |
| 打印绑定本机插件 | 多页直接调用 Lodop | 浏览器、驱动和部署环境依赖强 |
| 页面逻辑重复 | 列表、弹窗、分页和导出脚本大量复制 | 修复成本高，行为容易不一致 |
| 视觉层级混杂 | Bootstrap、EasyUI、zTree、大屏和内联 CSS 并存 | 同一系统存在多套交互与颜色规则 |

## 19. 新前端还原原则

新前端应还原老系统的信息架构和业务能力，不还原老技术债：

1. 保留 11 个一级菜单、68 个业务入口及其顺序，使用 Vue Router 和权限路由替代 JSP/iframe。
2. 保留顶栏、左侧分组导航、可关闭页签和中央工作区，桌面端维持高信息密度。
3. 列表页统一为页面标题、紧凑筛选、操作栏、数据表和分页，不使用大面积指标卡替代业务表格。
4. 订单详情按订单、处方、药品、金额、配送、审核/调剂/复核留痕分段，避免单表无限横向扩展。
5. 新增/编辑使用 TDesign Dialog/Drawer 和类型化表单；保存成功后明确刷新来源列表。
6. 大屏保持独立深色全屏模式；打印保持固定纸张和标签尺寸；二者不套普通后台布局。
7. 所有页面补齐加载、空数据、接口错误、无权限、只读、禁用和提交中状态。
8. 桌面端以 1366/1440px 为主要作业宽度，表格允许受控横向滚动；移动端保留查询和查看能力，复杂生产操作可明确限制为桌面端。
9. 用户主界面展示机构名、处方号、患者名和业务状态，技术 ID 放在详情或诊断信息中。
10. 打印、导入、导出、批量操作和权限变更必须有任务结果、失败原因与审计记录。

# 新项目后端代码审查报告

## 1. 审查范围

审查日期：2026-08-04。

本报告以 `00_项目总览/老项目审查报告.md` 中的旧系统业务能力为基线，审查当前 `backend` 的 13 个运行服务、公共模块、42 个 Flyway migration、管理端接口、状态机、异步任务和部署配置。该报告描述新项目现状，不修改老项目审查结论。

## 2. 总体结论

当前后端不需要推倒重写，但在作为完整生产替代版本前，必须修改权限与租户隔离、跨服务事务、数据所有权和异步任务并发控制。现有订单幂等、条件状态更新、Outbox 发布、消息消费幂等、PDA/MES 操作幂等、物流轨迹和报表查询可以保留。

建议顺序：

1. 先完成管理端认证、RBAC、租户上下文和数据权限。
2. 再修复工作流、煎煮、物流的跨服务一致性。
3. 随后补 callback/integration 多实例任务认领。
4. 再收敛服务和表所有权，拆分 `order-service` 内部大模块。
5. 最后按老系统基线补批量导入、任务领取、短信群发、真实面单/打印等能力。

## 3. 风险分级

| 等级 | 问题 | 影响 | 处理要求 |
| --- | --- | --- | --- |
| P0 | 管理端没有登录认证、角色/菜单授权和租户上下文 | 可直接调用 `/api/admin/**`；管理数据大量使用固定租户 | 上线前完成 |
| P0 | 工作流、煎煮、物流在本地事务内同步调用其他服务 | 远端成功、本地回滚后出现跨域状态不一致 | 改为本地事务 + Outbox/补偿，或收回同一聚合处理 |
| P0 | 多个服务共享同一 schema，migration 集中在 `order-service` | 服务无法独立演进，表变更影响全部服务 | 建立表和 migration 唯一所有者 |
| P1 | callback/integration 重试任务没有认领 | 多副本扫描可能重复发送外部请求 | 增加 CAS 认领或数据库跳锁 |
| P1 | `prescription-service` 是空壳，多个领域继续进入 `order-service` | 文档边界与代码边界不一致，大类继续增长 | 先内部模块化，再决定是否独立部署 |
| P1 | 旧系统部分能力没有后端闭环 | 前端存在入口但只能展示或执行部分操作 | 按业务矩阵补齐 |
| P1 | 旧 PDA 出库和人工流程可连续推进多个状态 | 可能绕过真实调剂、复核或煎煮事实 | 限定机构、权限、开关并完整审计 |
| P2 | Controller、Service、Repository 体积过大 | 修改成本和回归风险持续上升 | 随业务修复分模块拆解 |

## 4. 架构发现

### 4.1 管理端安全和租户隔离

- `InstitutionOrderController` 暴露大量 `/api/admin/**`，后端未引入 Spring Security、认证 Filter 或方法权限注解。
- `operator_user` 只有用户名、显示名、角色代码和启停状态，没有密码凭证、角色实体、菜单、角色菜单或用户角色关系。
- `OrderService`、导出、短信和煎煮管理逻辑存在固定默认租户 UUID。
- 旧系统已有用户、角色、菜单、角色授权和用户授权，因此当前不是简化实现，而是缺少完整权限域。

建议建立统一 `AdminPrincipal(userId, tenantId, institutionIds, roleIds, permissions)`。令牌必须由统一认证入口签发，各服务从可信上下文取得租户；高风险写操作必须校验按钮权限、数据范围并记录操作审计。

### 4.2 服务和数据边界

- 除空壳 `prescription-service` 外，业务服务均直接连接 `zhyf_saas`。
- V1-V42 migration 同时创建订单、处方、工作流、煎煮、物流、回调、集成、短信和机构权限表。
- 多个服务直接读取订单表，`order-service` 又直接维护机构、药品、物流配置、标签和部分流程数据。
- `auth-institution` 查询机构应用，但机构管理写入仍在 `order-service`，形成双重所有者。

短期不建议继续增加空壳服务，也不建议立即物理分库。先建立单表唯一写入所有者，禁止新增跨域写 SQL；跨域读取逐步改为稳定 Query API 或只读投影。是否拆库应由独立扩缩容、团队边界和故障隔离需求决定。

### 4.3 `order-service` 集中度

- `InstitutionOrderController` 约 1292 行、100 个路由。
- `OrderService` 约 3672 行。
- `OrderRepository` 约 6215 行。
- `prescription-service` 只有启动骨架。

建议先保持 URL 和数据库不变，在 `order-service` 内按订单、处方、平台配置、药品、机构管理、打印和物流配置拆 Controller、应用服务和 Repository。处方模块稳定后再决定迁入 `prescription-service`，没有独立部署价值时应明确采用模块化单体并移除空壳部署单元。

## 5. 业务一致性发现

### 5.1 跨服务 HTTP 位于本地事务中

- 审方和复核先调用订单服务，再更新本地 workflow task。
- 煎煮开始、完成、终止先推进订单状态，再更新本地煎煮任务。
- 物流打包、发货和轨迹推进在事务内调用订单服务和 callback-service。

当远端成功、本地 SQL 失败时，本地事务无法回滚远端事实。这与 `03_架构设计/事务一致性设计.md` 的规则相反。

建议由工作流、煎煮和物流服务在本地事务内写业务表、操作日志和 Outbox；订单服务消费领域事件后更新订单总状态。失败进入可查询、可重试、可人工处理的补偿状态，不引入 XA/2PC。

### 5.2 异步任务并发

Outbox 扫描会先通过状态条件更新认领 `PUBLISHING`，并有超时释放，可以保留。callback 和 integration 只查询到期任务后直接发送，没有 `PROCESSING` 认领，多实例下存在重复发送风险。

建议增加 `PROCESSING`、`claimed_by`、`claimed_at`，通过条件更新批量认领并支持超时释放；外部调用携带稳定幂等键。生产启动时应校验自动派发开关，不依赖静默默认值。

### 5.3 状态机和兼容跳转

订单状态机、当前状态条件更新和状态日志主体合理。调剂作为子任务存在但没有进入订单状态，订单进度 DTO 应明确展示调剂事实，煎煮入口必须验证调剂和复核均已完成。

旧 PDA 出库可从 `RECHECKED` 连续推进到煎煮、打包和发货；人工流程也会批量补写状态日志。这类逻辑只能作为指定机构兼容策略，必须有机构开关、专用权限、原因、原始请求和异常告警。

## 6. 老系统能力对照

| 能力域 | 当前状态 | 主要缺口 |
| --- | --- | --- |
| 用户/角色/菜单 | 操作员 CRUD、角色代码聚合 | 登录、凭证、角色菜单、授权、数据权限、接口鉴权 |
| 参数配置 | 字典、参数、煎煮中心、工号基础 CRUD | 删除/停用规则、变更审计、租户隔离 |
| 机构接入 | 机构、应用、接口权限、白名单和签名主体存在 | 写入归属、密钥轮换、限流、灰度、审计 |
| 订单处方 | 查询、详情、修改、取消、审核、复核、回执、重打主体存在 | 任务锁、地址/处方变更历史、处方状态日志 |
| 药品主数据 | 目录、索引、区域、操作日志基础 CRUD | 文件模板、预检、批量导入、错误明细、匹配失败任务 |
| 流程作业 | 审核、调剂、复核任务可完成 | 领取/释放/超时、并发操作者校验、绩效事件、补偿 |
| 煎煮设备 | PDA/MES、设备、水桶、绑定和记录较完整 | 模拟器与生产领域服务解耦、跨服务事件化 |
| 物流履约 | 打包、发货、轨迹、签收、规则和合单主体存在 | 真实承运商下单/取消/面单、打印任务、未签收跟进 |
| 短信标签 | 模板、单发、记录、标签和打印记录存在 | 群发、失败重试、余额/供应商状态、真实打印回传 |
| 报表对账 | 主要汇总、明细和 CSV 较完整 | 口径验收、异步大导出、租户/机构数据权限 |
| 运维补偿 | Outbox、消费、死信、问题件和健康概览存在 | 领域不一致检查、任务认领、补偿权限和审计 |
| 外围集成 | 旧协议、医院查单、地址补录和重试主体存在 | 契约回归、密钥治理、派发开关和重复发送保护 |

代码中未发现后端文件导入端点或导入任务模型；短信仅有单发端点；物流打印接口仍返回等待外部承运商配置。因此不能按前端页面存在判定这些能力完成。

## 7. 实施顺序

### 7.1 生产阻断项

1. 管理端认证、RBAC、租户上下文和数据权限。
2. 工作流、煎煮、物流跨服务事务改造和补偿查询。
3. callback/integration 任务认领、超时释放和多实例测试。
4. 移除生产数据库地址和敏感配置默认值，启动时校验必填环境变量。

### 7.2 边界收敛

1. 拆分 `order-service` 内部业务模块。
2. 确定处方模块真实部署形态。
3. 建立表和 migration 所有权清单。
4. 将机构管理写入迁回机构认证域，其他过渡模块保持明确边界。

### 7.3 能力补齐

1. 药品、索引、区域、物流地址费用和订单回执批量导入。
2. 工作流任务领取、处方/地址变更历史、短信群发和失败重试。
3. 真实面单、打印任务、结果回传和未签收跟进。
4. 老机构协议固定报文、签名、映射和错误码契约测试。

## 8. 可保留实现

- 外部订单号唯一约束和重复下单幂等返回。
- 订单状态机、条件更新和状态日志主体。
- Outbox CAS 发布、失败重试、超时释放和 DEAD 记录。
- MQ 消费日志唯一约束和处理中超时恢复。
- PDA/MES `operation_id` 与物流轨迹业务事件唯一约束。
- 报表服务只读查询和 CSV 端点。

## 9. 验证记录

使用 JDK 21 执行 `backend/mvn test`，15 个 Maven reactor 模块构建成功，现有 193 个测试全部通过。`auth-institution` 和 `prescription-service` 没有测试；现有测试主要是单元和 SQL 映射测试，尚未覆盖跨服务一致性、多实例认领、管理端越权、跨租户访问和完整旧协议契约。

后续至少补充：管理端未认证/越权/跨租户测试；工作流、煎煮、物流远端成功但本地失败的补偿测试；callback/integration 双实例认领测试；旧协议样例端到端契约测试。

# 老项目前端解析

## 1. 解析范围

本文合并 `docs` 中关于老后台 UI、菜单、JSP 页面和当前前端重构方案的内容，并补充对老项目源码的静态核对结果。

主要依据：

- 老后台工程：`D:\workproject\chengyou\1\zhyfsupport`
- 老 JSP 目录：`src/main/webapp/WEB-INF/jsp`
- 老后台控制器：`src/main/java/com/zhyf/support/controller`
- 现有审查文档：`docs/00_项目总览/老项目审查报告.md`
- UI 截图基线：`docs/00_项目总览/老项目UI截图基线`
- 当前前端方案：`docs/03_架构设计/前端架构重构方案.md`

本文只解析页面结构、菜单、交互和迁移边界，不作为视觉稿或代码实现说明。

## 2. 老前端技术形态

老后台是传统 Java Web 管理端：

- 页面：JSP、HTML、iframe、Bootstrap Modal、少量 EasyUI/zTree 类插件。
- 脚本：jQuery、页面内联脚本、Lodop 打印、My97DatePicker。
- 布局：顶部栏、左侧菜单、可关闭页签、中央 iframe 工作区。
- 路由：菜单中的 `.html` 入口最终由 Spring MVC Controller 返回 JSP 或 JSON。
- 样式：页面级 CSS、内联样式、固定像素宽度和多套插件样式混用。

新前端不应该复制 JSP、iframe、jQuery、Bootstrap 旧实现，但必须保留老系统的信息架构、菜单粒度、作业顺序和字段密度。

## 3. 应用壳层结构

老系统主工作流为：

```text
登录页
 -> 后台主框架
 -> 左侧一级菜单/二级菜单
 -> 顶部工作页签
 -> iframe 打开业务 JSP
 -> 列表、筛选、详情、弹窗、打印或导出
```

新前端应保留的业务结构：

- 顶栏：产品名、当前用户、退出入口。
- 左侧导航：11 个一级菜单，按老系统顺序展示。
- 页签栏：允许多业务页面并行处理，支持关闭和切换。
- 工作区：以列表、详情、工作台、导入、打印、报表为主。

不应保留的技术结构：

- iframe 承载业务页。
- JSP 之间通过 `parent` 调用互相刷新。
- 全局脚本操作 DOM。
- 固定宽度表格包住整个页面。
- 业务页面直接调用本机 Lodop 而无任务状态。

## 4. 一级菜单和业务入口

老后台菜单基线为 11 个一级菜单、68 个老业务入口。当前新系统另有若干新增入口，例如工作台、门户查单、集成任务、导出任务中心、机构应用配置等，但这些新增入口不能替代老菜单。

| 一级菜单 | 老业务入口数 | 迁移要求 |
| --- | ---: | --- |
| 系统管理 | 3 | 用户、角色、菜单必须保持独立页面 |
| 参数管理 | 4 | 字典、参数、煎煮中心、工号独立维护 |
| 机构管理 | 4 | 机构、白名单、接口、接口权限独立维护；新系统可新增机构应用配置 |
| 物流管理 | 7 | 规则、地址费用、发货、轨迹、打单、合单、未签收跟进分开 |
| 订单管理 | 14 | 是最复杂模块，不能用一个通用表格代替 |
| 维护管理 | 4 | 订单流程、异常日志、MQ 消息、问题件 |
| 标签管理 | 2 | 标签模板和标签打印必须保留固定尺寸逻辑 |
| 短信管理 | 3 | 模板、单发、发送记录分开 |
| 药品管理 | 6 | 药品目录、索引、导入、区域、操作日志 |
| 报表管理 | 16 | 汇总报表和明细报表成对存在 |
| 煎煮管理 | 5 | 设备、绑定、PDA/打码机、加水桶、云打印记录 |

## 5. JSP 页面分布

老 JSP 目录核对到 98 个业务 JSP，另有登录、首页、错误页、授权页等框架和系统页。

| 目录 | 页面类型 |
| --- | --- |
| 根目录 | `index.jsp`、`login.jsp`、`default.jsp`、用户、角色、菜单、授权、错误反馈 |
| `systemSetting` | 字典、系统参数、煎煮中心、工号 |
| `mechanism` | 机构、IP 白名单、接口、接口权限 |
| `order` | 订单、处方、审核、调剂、复核、地址修改、处方修改、签收、流程等 |
| `logistics` | 物流规则、费用、发货、轨迹、打单、合单、未签收 |
| `decoct` | 设备、处方设备绑定、PDA/打码机、加水桶、云打印 |
| `lableset` | 标签设置、标签打印、标签模板片段 |
| `sms` | 短信模板、单发短信、短信记录 |
| `drugManage` | 药品目录、药品索引、导入、区域、操作日志 |
| `report` | 处方、机构、人员绩效、药材、对账、物流等报表 |
| `mainten` | 流程查询、异常日志、MQ 消息、问题件 |

## 6. 关键页面类型

老系统页面不能全部抽象成一种“卡片列表”。至少存在以下页面类型：

| 页面类型 | 老系统表现 | 新前端承接方式 |
| --- | --- | --- |
| 标准列表页 | 标题、紧凑筛选、表格、分页、导出 | `ListPage`、`SearchToolbar`、`DataTable` |
| 配置 CRUD | 列表 + 新增/编辑弹窗 | Drawer/Dialog 表单 |
| 订单详情 | 多段信息、处方分组、药品明细、流程痕迹 | 独立详情页或右侧工作台 |
| 审核/调剂/复核 | 有状态约束和操作区 | 独立工作台，不做静态详情 |
| 导入页 | 模板、文件、预检、结果 | 导入向导 |
| 打印页 | A5、标签、二维码、条码、固定尺寸 | 打印工作台和任务记录 |
| 报表页 | 时间/机构/人员筛选、汇总、明细、导出 | 汇总页和明细页保持钻取 |
| 运维排障页 | 按订单号、时间、状态定位问题 | 业务阶段优先，技术字段放诊断区 |

## 7. 订单管理 UI 解析

订单管理是老后台核心，不是单一“处方列表”。

老订单菜单包括：

- 处方列表：`order/listOrder.html`
- 订单审核：`order/listExamineOrder.html`
- 调剂打印：`order/listAdjustOrder.html`
- 处方复核：`order/review.html`
- 处方复核（多桶）：`order/reviews.html`
- 复核管理：`order/listReview.html`
- 订单地址修改：`order/listModifyAddress.html`
- 处方修改：`order/listModifyPrescri.html`
- 订单操作：`order/listManageOrder.html`
- 处方重打：`order/listPrescriptionReprint.html`
- 订单仓库：`order/listOrderWarehouse.html`
- 订单拦截配置：`order/listFillpushPrescriptionsIntercept.html`
- 订单走流程：`order/listProcessOrder.html`
- 订单签收：`order/listOrderReceipt.html`

订单详情页必须展示：

- 订单信息：平台订单号、机构、订单状态、订单时间、配送方式、物流公司、物流单号、签收时间、收件人、地址、备注。
- 处方信息：平台处方号、机构处方号、处方类型、患者姓名、性别、年龄、科室、病区、床号、医生、诊断、用法、剂数、包装量、煎煮要求。
- 药品明细：机构药品编码/名称、平台药品编码/名称、剂量、单位、特殊用法、规格、产地、销售价、结算价。
- 流程信息：审核、调剂、复核、煎煮、打包、发货、签收的操作人、时间和原因。

新前端不能只迁移列表；必须保留审核、调剂、复核、地址修改、处方修改、签收和手动推进这些作业入口。

## 8. 物流 UI 解析

物流模块不是单纯轨迹查询。老系统中物流承担规则配置、发货操作、打单、合单和未签收跟进。

页面基线：

- 机构物流费规则配置
- 机构地址物流费配置
- 订单发货查询
- 物流信息查询
- 物流打单
- 物流合并列表
- 未签收跟进

迁移要求：

- 规则配置页保持标准 CRUD。
- 发货页区分待发货、已发货、签收状态。
- 打印页保留固定纸张和条码/二维码。
- 合单页必须显示被合并订单、合单状态和取消合单动作。
- 未签收跟进必须有跟进记录、原因和下次处理时间。

## 9. 煎煮、标签和打印 UI 解析

煎煮相关页面包含设备档案和生产作业记录：

- 设备列表查询
- 处方设备绑定列表
- 打码机打印配置
- 加水桶管理
- 云打印记录列表

标签管理包含：

- 代煎标签设置
- 代煎标签打印

迁移要求：

- 设备列表使用稳定表格，不做营销式卡片。
- 绑定记录必须保留处方、设备、加水桶、操作状态、操作人和时间。
- 标签和面单预览使用固定尺寸，不随普通响应式布局缩放。
- 打印动作要有任务状态、失败原因和重打原因。

## 10. 报表 UI 解析

老报表管理共有 16 个入口，不能合并成一个“报表总览”后丢失明细。

报表分组：

- 数量统计：处方数量、机构处方数量。
- 人员绩效：审核员、调剂员、复核员、煎煮员、物流员，均有统计和明细。
- 药材和对账：机构药材统计、处方对账、药材明细、药材用量。

迁移要求：

- 汇总和明细保留独立路由。
- 时间、机构、人员筛选保持高密度。
- 金额、剂量、数量、时间统一格式化。
- 大范围查询建议转异步导出任务。

## 11. 当前新前端对照

当前项目中前端仍是 `frontend/admin-web`，技术栈为 Vue 3、TypeScript、Vite、Vue Router。之前文档里已有 React 重建计划，但当前运行代码并未完成 React 替换。

已存在的能力：

- `views.ts` 已维护老菜单顺序、路径和部分权限信息。
- `route-components.ts` 已将多个页面挂到真实组件。
- 订单、机构、物流、报表、煎煮、短信、标签、药品等已有不少 Vue 页面。

主要缺口：

- 运行代码仍是 Vue，不是 React。
- 多个老菜单入口复用同一个聚合工作区，不能视为完整迁移。
- 一些页面有真实查询和操作，一些页面仍偏“壳”或简化流程。
- 旧 UI 布局有参考价值，但旧样式、iframe 和 Lodop 调用方式不能照搬。
- 当前页面是否“完成”必须按老菜单逐页验收，而不能只看路由是否存在。

## 12. 前端迁移验收清单

每个页面完成前至少核对：

- 是否保留老菜单入口、名称、顺序和业务粒度。
- 是否有真实筛选、表格、分页、空态、错误态、无权限态。
- 是否保留老页面关键业务字段，而不是只展示摘要。
- 是否保留行内动作、批量动作、导入、导出、打印等业务能力。
- 高风险动作是否有状态校验、二次确认、原因字段和审计记录。
- 订单、处方、患者、机构、物流状态是否显示中文业务文案。
- UUID、内部端口、技术编码是否退出主信息区。
- 1440、1366、768、390 宽度下菜单、页签、筛选和表格是否可用。
- 打印页是否验证固定纸张尺寸。

## 13. 后续执行建议

如果继续改前端，应按以下顺序：

1. 固定老菜单和 UI 截图基线，确认 11 个父级菜单逐项可达。
2. 先重建应用壳层：顶栏、侧栏、页签、工作区、移动端 Drawer。
3. 迁移系统、参数、机构、药品等 CRUD 页面，形成统一列表和表单规范。
4. 再迁移订单主链路：处方列表、详情、审核、调剂、复核、地址修改、签收。
5. 最后迁移物流、煎煮、标签、短信、报表、维护和打印类复杂页面。
6. 若确认替换为 React，应停止继续扩 Vue 页面，先建立 React 路由、菜单、API 客户端和组件规范，再分阶段替换。

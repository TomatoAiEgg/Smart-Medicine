## 2. 老后端整体结构

老系统不是单一后端，而是两个主要 Java 工程围绕同一套 MySQL 业务库协作。

| 工程 | 技术栈 | 职责 |
| --- | --- | --- |
| `zhyfsupport` | Spring MVC、JSP、MyBatis、Maven WAR | 内部运营后台，负责菜单、用户、机构、参数、订单、物流、药品、报表、维护等 |
| `zhyf-api` | Spring Boot 1.5、Spring Cloud Edgware、MyBatis、ActiveMQ | 外部机构接口、PDA/MES/物流接口、签名校验、IP 白名单、订单写入、异步任务 |

`zhyf-api` 包含三个模块：

| 模块 | 职责 |
| --- | --- |
| `zhyf-common` | 公共实体、枚举、常量、DTO、工具类 |
| `zhyf-gateway` | 外部 API、PDA/MES/物流接口、鉴权、入库、消息生产 |
| `zhyf-async` | ActiveMQ 消费、订单校验、审方、短信、状态回调、定时任务 |

## 4. 订单后台核心能力

`OrderController` 是老后台最复杂控制器，核心入口包括：

- `/order/listOrder`：处方/订单列表。
- `/order/getOrderInfo`：订单详情。
- `/order/listExamineOrder`、`/order/saveExamineOrderInfo`：审核。
- `/order/listAdjustOrder`、`/order/adjustPrescription`：调剂和打印。
- `/order/review`、`/order/reviews`、`/order/reviewPrescription`：单桶/多桶复核。
- `/order/listModifyAddress`、`/order/modifyAddress`、`/order/modifyAddresses`：单个/批量地址修改。
- `/order/listModifyPrescri`、`/order/modifyPrescri`：处方修改。
- `/order/listManageOrder`、`/order/initializePrescriptionStatus`、`/order/cancelPrescriptionStatus`：订单管理操作。
- `/order/listPrescriptionReprint`、`/order/prescriptionReprint`：处方重打。
- `/order/listFillpushPrescriptionsIntercept`：订单拦截配置。
- `/order/listProcessOrder`、`/order/processOrder`：手动走流程。
- `/order/listOrderReceipt`、`/order/orderReceipt`、`/order/batchOrderReceipt`：签收。
- `/order/splitOrder`：拆单。

关键业务规则：

- 审核通过后会更新审核字段、日志和后续状态。
- 调剂打印不只是打印按钮，会影响处方打印状态和流程记录。
- 复核会校验水量、加水桶、处方状态，并写入绑定信息。
- 地址修改可能触发合单、校验和回调相关流程。
- 处方修改会影响煎煮时间、包装量、用法、备注和校验任务。
- 手动走流程会补齐审核、复核、物流、签收等节点日志。
- 拆单会创建新订单、新处方、新明细，并保留原处方关系。

## 5. `zhyf-api` 对外接口

老 API 入口主要在 `zhyf-gateway`。

### 5.1 通用订单接口

`OrderApiController` 暴露：

- `/healthCheck`
- `/createOrder`
- `/cancelOrder`
- `/queryOrder`
- `/updateOrderAddress`
- `/getOrderId`

`createOrder` 主要流程：

1. 读取请求头、签名参数和订单报文。
2. 根据 appKey、接口编码、IP 白名单、签名进行校验。
3. 使用 Redis 锁避免重复请求。
4. 按机构处方号做重复订单检查。
5. 生成老平台订单号。
6. 写入 `zhyf_order`、`zhyf_prescription`、`zhyf_prescription_details`。
7. 初始化物流信息。
8. 发送 `createOrderSuccess.service.queue`。

### 5.2 智慧云接口

`SmartCloudOrderApiController` 路径前缀为 `/zhy`，暴露：

- `/zhy/healthCheck`
- `/zhy/syncHospitalRecipel`
- `/zhy/modHospitalRecipel`
- `/zhy/cancelRecipel`
- `/zhy/recipeStatusCallback`

特点：

- 报文字段不同于通用 `/createOrder`，包含 `hospitalid`、`outtradeno`、`patient`、`hospital`、`recipel`、`express`、`drug` 等节点。
- 签名逻辑对嵌套字段有特殊排序和拼接规则。
- 部分机构存在硬编码式分支，例如按院区/科室映射机构编号。
- 创建订单仍落到老订单、处方、明细表。

## 6. 鉴权和接入控制

老系统机构接入控制由以下表和逻辑组成：

- `zhyf_institutions`：机构档案、机构编码、回调配置、默认收件信息、上线状态。
- `zhyf_api_info`：接口定义。
- `zhyf_api_permission`：机构接口授权。
- `zhyf_white_ip`：机构 IP 白名单。
- `zhyf_system_config`：部分全局参数。

通用校验包含：

- appKey 是否存在。
- 机构是否启用。
- 调用接口是否登记。
- 机构是否有该接口权限。
- 来源 IP 是否在白名单。
- 时间戳是否过期。
- 签名是否匹配。
- 是否重复请求或重复处方。

新系统应把这些能力放在 gateway 和 auth/institution 域，且写入访问日志，不能只做前端按钮可见性控制。

## 7. 订单号生成规则

老订单号由 `OrderIdServiceImpl.getOrderID()` 生成。

规则：

- 前缀来自系统配置 `CFG_ORDER_ID_PREFIX`。
- 时间部分格式为 `yyMMddHHmm`。
- 序号为当天最大订单号基础上递增的 5 位数。
- 序号超过 `99999` 时会报错。
- 生成时会从数据库读取当天最大订单号。

当前新系统若继续使用 `ZHYF + epochMillis`，就不能和老系统订单号规则保持一致。兼容老接口时必须明确：对外返回老格式，或提供双号映射。

## 8. 状态模型

老系统订单状态是数字码：

| 老状态码 | 名称 |
| ---: | --- |
| 1 | 已创建 |
| 5 | 审核中 |
| 8 | 待确认 |
| 15 | 调剂中 |
| 20 | 复核完成 |
| 23 | 已浸泡 |
| 25 | 煎煮中 |
| 27 | 煎煮完成 |
| 28 | 包装完成 |
| 29 | 质检完成 |
| 40 | 派送完毕/签收完成 |
| 97 | 用户拒收 |
| 98 | 审核失败 |
| 99 | 用户取消 |

当前新系统状态更偏领域枚举，例如 `CREATED`、`AUDIT_PASSED`、`RECHECKED`、`DECOCTING`、`DECOCTED`、`PACKED`、`SHIPPED`、`IN_TRANSIT`、`SIGNED`、`CANCELLED`、`AUDIT_FAILED`。

迁移要求：

- 内部状态可以使用英文枚举。
- 对老接口和老迁移数据必须建立数字状态映射。
- 不同维度状态应拆分：订单状态、处方状态、生产任务状态、物流状态、异常状态。
- 状态推进必须由服务层或状态机统一处理。
- 所有状态变化必须写日志，并具备并发保护。

## 9. ActiveMQ 异步链路

老系统 ActiveMQ 队列：

| 队列 | 用途 |
| --- | --- |
| `createOrderSuccess.service.queue` | 订单创建成功后的药品匹配、处方校验、审方等统一处理 |
| `reviewFinishPushRecipe.service.queue` | 复核完成后推送处方 |
| `sendMsgMessageMQ.service.queue` | 短信发送 |
| `orderInfoValidationMQ.service.queue` | 订单/处方信息校验 |
| `threeAudit.service.queue` | 三方审方 |
| `orderStatusChange.service.queue` | 订单状态变化回调 |

主要消费者：

- `ActiveMqConsumer`：订单创建后处理、复核推送、状态变化回调。
- `OrderValidationListener`：订单信息校验。
- `SendMsgListener`：短信消息。
- `ThreeAuditListener`：三方审方。

定时任务：

- 机构在线状态检查。
- 短信补发。
- 控制台/统计类任务。

新系统使用 RocketMQ 和 Outbox 时，不能只替换消息中间件名称，还要保留幂等、重试、死信、任务认领、业务日志和人工补偿。

## 11. 后端迁移优先级

建议执行顺序：

1. 建立老接口契约清单：路径、方法、签名、请求字段、响应码、状态码。
2. 补齐老订单号生成器和双号映射。
3. 建立老数字状态到新状态机的完整映射。
4. 逐个补齐 `/createOrder`、`/zhy/syncHospitalRecipel`、`/szlgzx/zhyfCreateOrder` 的字段解析测试。
5. 补齐取消、查单、地址修改、状态回调。
6. 补齐 PDA、MES、物流接口的作业状态和幂等规则。
7. 将 ActiveMQ 旧队列语义映射到 RocketMQ topic/event/outbox。
8. 后台管理 API 按老菜单补齐：订单、物流、煎煮、报表、维护、短信、标签。
9. 对所有兼容接口建立契约测试和脱敏样例报文。

## 12. 验收标准

后端不能只按“接口存在”验收，应满足：

- 老路径可访问。
- 老签名规则可验证。
- 老请求字段可解析。
- 老响应码和业务状态能按契约返回。
- 订单号符合约定或有明确双号映射。
- 状态推进写入状态日志。
- 重复请求、重复处方、重复 MQ 消费具备幂等保护。
- 回调失败可重试、可查询、可人工补偿。
- 后台页面所需查询、导出、打印、操作接口可完整调用。
- 所有敏感字段不进入日志和文档。

## 13. 2026-08-16 后端功能迁移对照结论

本次按老 `zhyfsupport`、老 `zhyf-api` 和当前 `backend` 做静态入口盘点，并结合开发测试库导入后的接口验证结果复核。结论是：当前后端已经搭起多服务架构、老协议兼容入口和大量后台 API，但不能判定为“老后端功能已全量移植”。现在属于“数据底座已导入、核心入口部分承接、业务细节和契约验收仍有缺口”的阶段。

### 13.1 入口规模对照

| 范围 | 扫描结果 | 说明 |
| --- | ---: | --- |
| 老后台 `zhyfsupport` | 19 个 Controller，约 304 个 Spring MVC 注解 | 页面跳转、查询、导出、打印和状态推进耦合在 Controller 中 |
| 老接口 `zhyf-api` | 11 个 Controller/入口类，约 60 个 Spring MVC 注解 | 通用订单、智慧云、龙岗中心医院、PDA、MES、物流和异步测试入口 |
| 当前新后端 `backend` | 29 个 Controller，约 304 个 Spring Web 注解 | 多服务拆分后入口数量已接近老后台规模，但入口存在不代表契约完整 |

当前新后端已存在 `LegacyOrderApiController`、`LegacySmartCloudOrderController`、`LegacySzlgzxyyOrderController`、`LegacyPdaProtocolController`、`LegacyMesProtocolController`、`LegacyLogisticsController`、`InstitutionOrderController`、`WorkflowReviewTaskController`、`AdminDecoctionController`、`LogisticsAdminController`、`ReportController`、`OpsQueryController` 等入口。

开发测试库已经导入老库数据用于生产化开发验证，文档只记录表级计数和迁移结论，不记录真实患者、订单明细或任何凭据。

| 数据范围 | 当前状态 | 说明 |
| --- | --- | --- |
| 老库原始数据 | 已导入 `legacy_mysql` 原始 schema | 原始 37 张表、约 231.87 万行，保留老数据形态供对照 |

### 13.4 当前不能算“全量移植完成”的证据

- 旧协议入口已存在，但 `LegacySmartCloudOrderController.recipeStatusCallback` 仍返回“状态回调未接入”，并记录 `NOT_IMPLEMENTED`。
- `LogisticsService.printWaybill`、`queryEmsPdfFile` 明确返回外部承运商/EMS 服务待配置状态，真实电子面单和 PDF 拉取未完成闭环。
- 管理端订单列表在生产量级数据下有 RLS 查询性能缺口，影响前端联调和运营使用。
- 老后台 `OrderController`、`LogisticsController`、`ExportExcelController` 中大量导出、打印、状态推进和特殊业务动作，当前只完成了部分 API 入口和代表链路，缺少逐页面、逐按钮验收记录。
- 老系统 ActiveMQ 队列语义已迁到 RocketMQ/Outbox 的方向，但还未形成完整的旧队列到新事件、重试、死信、人工补偿矩阵。

### 13.5 建议后续执行顺序

1. 先修 `OrderRepository.searchAdminOrders` 的分页查询结构，解决生产数据下订单列表不可用风险。
2. 建立老接口契约测试集：通用订单、智慧云、龙岗中心医院、PDA、MES、物流，每个接口至少覆盖成功、字段缺失、签名错误、无权限、重复请求和状态不允许。
3. 按老后台截图和 Controller 清单逐页做管理端 API 验收，特别是订单、物流、煎煮、报表导出和维护补偿。
4. 补齐外部承运商电子面单、EMS PDF、状态回调和失败补偿；若当前开发期不接真实承运商，也要明确模拟实现和生产切换点。
5. 建立老数字状态到新状态机的最终矩阵，并让所有 legacy 响应、后台列表、回调和日志共用同一套映射。

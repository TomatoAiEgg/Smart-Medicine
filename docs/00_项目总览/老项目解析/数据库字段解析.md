# 老项目数据库字段解析

## 1. 解析范围

本文合并 `docs` 中关于老 MySQL 表、PostgreSQL 重构设计、字段迁移和当前项目表设计的内容，并补充从老 MyBatis XML、实体和业务代码中核对到的字段语义。

主要依据：

- 老后台工程：`D:\workproject\chengyou\1\zhyfsupport`
- 老接口工程：`D:\workproject\chengyou\1\zhyf-api`
- 现有文档：`docs/数据设计/数据库重构设计.md`
- 现有文档：`docs/00_项目总览/老项目审查报告.md`
- 老 MyBatis 映射：`src/main/resources/mybatis/**/*.xml`
- 当前 PostgreSQL/Flyway：`backend/**/src/main/resources/db/migration`

本文只记录表结构和字段语义，不记录生产连接信息、密码、真实患者数据或真实订单数据。

## 2. 老库总体判断

老系统数据库是多个 Java 应用共享的集中式业务库。老表设计的特点：

- 订单、处方、处方明细是核心。
- 机构、接口权限、白名单直接参与外部接入鉴权。
- 订单状态、处方状态、生产作业状态、物流状态混在多个表和字段中。
- 后台操作、MQ 消息、异常日志、短信、打印、物流轨迹都有记录表。
- 部分表承担多个语义，例如 `zhyf_prescription` 同时放患者、医生、审核、调剂、复核、煎煮、费用字段。
- 老表不能原样照搬到新系统，但字段语义必须被新模型承接。

## 4. 订单表 `zhyf_order`

### 4.1 业务语义

`zhyf_order` 是老平台订单主表，承载机构订单、收货信息、物流信息、费用、状态和部分流程时间。

关键字段：

| 字段 | 语义 | 新系统承接 |
| --- | --- | --- |
| `order_id` | 老平台订单号 | `order_no` 或 `legacy_order_no`，需明确双号策略 |
| `company_num` | 机构编码 | `institution.legacy_company_num` / `order_main.institution_id` |
| `storage_type` | 煎煮中心/仓储类型 | 订单履约配置或煎煮中心字段 |
| `order_status` | 老数字订单状态 | 内部状态机 + 老状态映射 |
| `order_status_follow` | 字符串状态轨迹 | 拆为 `order_status_log` |
| `province`、`city`、`zone`、`addr_detail` | 收货地址 | `order_receiver_address` |
| `consignee`、`tel` | 收件人和电话 | `order_receiver_address` |
| `callback_url` | 机构回调地址 | 机构回调配置快照或 callback 记录 |
| `logistics_company_num`、`logistics_company_name` | 物流公司 | `shipment` / 物流快照 |
| `logistics_no` | 物流单号 | `shipment.logistics_no` |
| `logistics_status` | 物流状态 | `shipment.status` / 映射状态 |
| `package_time`、`outbound_time`、`sign_time` | 打包、出库、签收时间 | 订单状态日志和物流事件 |
| `order_pkg_weight`、`order_pkg_num` | 包裹重量和数量 | 物流包裹字段 |
| `logistics_money`、`logistics_receivables_money` | 物流费用和代收金额 | 物流费用记录 |
| `version` | 乐观锁/版本 | 新核心表必须保留并发控制 |

### 4.2 迁移要求

- 旧 `order_id` 不能丢，必须可按老单号查单。
- 收货地址应从订单主表拆出，并记录修改历史。
- 物流事实建议由 `logistics-service` 管理，订单侧保留快照。
- 老状态轨迹字符串应迁移为多行状态日志。
- 订单号生成规则需与 `OrderIdServiceImpl` 对齐或建立双号映射。

## 5. 处方表 `zhyf_prescription`

### 5.1 业务语义

`zhyf_prescription` 是老系统最宽的核心表，混合了承接处方、患者、医生、费用、审核、调剂、复核、煎煮和住院字段。

关键字段分组：

| 字段组 | 代表字段 | 新系统承接 |
| --- | --- | --- |
| 处方标识 | `prescri_id`、`order_id`、`hos_prescri_num` | `prescription`，保留老处方号和机构处方号 |
| 机构归属 | `company_num` | `tenant_id`、`institution_id` |
| 处方类型 | `prescri_type` | 处方类型字典 |
| 剂数费用 | `amount`、`decoct_amount`、`decoct_unit_price`、`decoct_total_price`、`total_money` | 处方费用和履约字段 |
| 患者信息 | 姓名、性别、年龄、诊疗卡、身份证、电话、孕妇标记 | 处方患者快照，敏感字段需脱敏处理 |
| 医生诊断 | 医生、科室、诊断、备注 | 处方医疗信息快照 |
| 审核 | 审核人、审核时间、审核图片、审核原因、审核结果 | `prescription_audit_record` |
| 调剂 | 调剂员工号、调剂时间、调剂图片 | `prescription_dispense_record` |
| 复核 | 复核员工号、复核时间、复核图片 | `prescription_recheck_record` |
| 煎煮 | 浸泡、煎煮、出药、加水量、煎煮设备、包装量 | `prescription_decoction_profile` / `decoction_task` |
| 住院 | 科室、住院号、病区号、床位号、门诊住院标记 | 处方住院信息分组 |
| 校验 | `validation_result` | 处方校验记录或校验摘要 |
| 推送 | `push_flag` | 集成推送状态 |

### 5.2 迁移要求

- 处方主表应保留业务快照，但审核、调剂、复核、煎煮事件应拆成记录表。
- 患者字段不能进入文档样例或日志原文。
- 机构处方号 `hos_prescri_num` 是外部幂等和查询关键字段，必须建立索引。
- 处方和订单是一对多关系，不能假设一单一方。

## 7. 机构和接口权限字段

### 7.1 `zhyf_institutions`

关键字段语义：

- `company_num`：机构编码，是外部接口核心身份字段。
- `company_name`、`short_name`：机构名称和简称。
- 默认收件人、地址、电话：用于机构默认履约配置。
- `callback_url`：机构状态回调地址。
- `company_pass`：旧机构密钥/密码字段，迁移时不能明文继承。
- `online_status`：机构在线/启用状态。
- 处方标签、门诊/住院、煎煮中心等配置字段参与业务路由。

### 7.2 `zhyf_api_info`

用于维护外部接口定义：

- 接口编码/方法名。
- 接口名称。
- 请求路径或说明。
- 启停状态。
- 备注和更新时间。

### 7.3 `zhyf_api_permission`

用于维护机构到接口的授权关系：

- 机构编码。
- 接口编码。
- 授权状态。
- 创建/更新信息。

### 7.4 `zhyf_white_ip`

用于维护机构来源 IP 白名单：

- IP 或网段。
- 机构编码。
- 是否启用。
- 更新时间。

迁移要求：

- 新系统应拆分为 `institution`、`institution_app`、`institution_api_permission`、`institution_ip_whitelist`。
- `company_num` 保留为 `legacy_company_num`。
- 密钥重新发放或迁移为安全摘要，不明文写入文档和日志。
- 所有鉴权失败需要写访问日志，便于机构接入排障。

## 8. 系统权限字段

老表：

- `tb_user`
- `tb_role`
- `tb_menu`

关键问题：

- 用户密码为旧式摘要，不能作为新系统安全模型继续使用。
- 角色权限通过 `rights` 字符串承载，无法满足现代 RBAC 的按钮权限、接口权限和机构数据范围。
- 菜单表承担前端菜单入口，但不等于完整权限模型。

迁移建议：

- `admin_user`
- `admin_role`
- `admin_menu`
- `admin_permission`
- `admin_user_role`
- `admin_role_permission`
- 机构数据范围表
- 登录会话表

后台权限必须由后端校验，前端只做展示过滤。

- `(order_no, created_at desc)` 用于日志和观测。

## 17. 迁移规则

迁移时必须遵守：

- 所有结构变更走 Flyway。
- 不把旧生产连接信息写入仓库。
- 不导入订单生产数据作为默认测试数据。
- 患者、手机号、身份证等敏感字段进入样例前必须脱敏或使用合成数据。
- 保留旧主键和外部编号到 `legacy_*` 或 `external_*` 字段。
- 无法确定语义的字段进入 `legacy_extra` 或 `raw_payload`，但敏感内容要脱敏。
- 金额使用定点数值类型。
- 状态变更必须写状态日志。
- 高并发写表必须有唯一约束、乐观锁或幂等键。
- 外部原始报文可以保留用于排障，但不得泄露敏感字段。

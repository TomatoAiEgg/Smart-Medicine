# 后端架构重构方案

## 1. 重构目标

后端目标是承接 `zhyfsupport` 和 `zhyf-api` 的真实职责：

- 内部运营后台能力来自 `zhyfsupport`。
- 外部协议入口能力来自 `zhyf-api`。
- 新系统按领域服务拆分，但不破坏旧外部协议。
- 所有核心流程可追踪、可审计、可补偿、可监控。

## 2. 当前问题

当前新后端已有订单、流程、煎煮、物流、报表、运维等模块，但仍存在问题：

- 后台管理 API 覆盖不足。
- 部分接口偏向演示链路，不足以支撑老后台页面。
- 旧状态码和新枚举之间缺少正式映射。
- 旧系统打印、导入导出、权限菜单、字典缓存、短信、维护记录尚未完整承接。
- 外部接口兼容只覆盖了一部分 PDA/MES/物流路径。
- 当前仓储层存在较多手写持久化代码，继续扩展会造成重复 SQL、RowMapper 和类型转换成本过高。

## 3. 持久化框架选型

后端不再继续扩大手写持久化范围，统一改为：

- MyBatis-Plus：主持久化框架。
- MyBatis Mapper XML：复杂查询、报表、遗留字段映射。
- Flyway：数据库结构变更。
- PostgreSQL：新系统主库。

选择 MyBatis-Plus 的原因：

- 老项目本身就是 MyBatis 技术路线，团队理解成本低。
- 比 JPA 更适合旧系统复杂表结构、报表 SQL、状态流转和遗留字段映射。
- 比手写持久化代码少大量重复 CRUD、RowMapper、时间类型转换和参数绑定代码。
- Spring Boot 3 项目可以使用 `mybatis-plus-spring-boot3-starter`。

边界规则：

- Service 层不拼 SQL。
- Mapper 层承载 SQL 和对象映射。
- 简单 CRUD 使用 MyBatis-Plus BaseMapper。
- 复杂查询使用 XML。
- 数据库结构仍以 Flyway migration 为准。

事务一致性设计详见 [事务一致性设计.md](D:/workspace/包装项目/智能药房SaaS平台/docs/03_架构设计/事务一致性设计.md)。后端总体原则是：单服务使用本地事务保证强一致，跨服务使用 Outbox、RocketMQ、幂等、重试和补偿保证最终一致。

## 4. 服务边界

| 服务 | 主要职责 |
| --- | --- |
| `gateway` | 统一入口、路由、签名校验、IP 白名单、访问日志、限流 |
| `auth-institution` | 租户、机构、应用密钥、白名单、API 权限、后台用户权限基础 |
| `order-service` | 订单、处方基础数据、状态机、订单查询、订单后台操作 |
| `workflow-service` | 审方、调剂、复核任务和人工流程 |
| `decoction-service` | PDA、MES、加水桶、设备、煎煮任务、煎煮回调 |
| `logistics-service` | 物流配置、发货、打单、合单、签收、物流回调 |
| `report-service` | 报表查询、统计口径、导出 |
| `ops-service` | MQ、异常、订单流程、回调失败、重试、健康概览 |
| `callback-service` | 对机构状态回调、失败重试、死信 |
| `integration-service` | 社康、医院查单、地址补录等外围系统适配 |
| `portal-service` | 医院侧查单、地址补录轻量入口 |
| `message-service` | Outbox 扫描、RocketMQ 发布、消费幂等 |

## 5. 后台管理 API 设计

后台管理 API 统一使用：

```text
/api/admin/**
```

外部旧协议兼容保留原路径或通过 gateway 转发：

```text
/createOrder
/cancelOrder
/queryOrder
/updateOrderAddress
/pdaUserLogin
/pdaBindPrescription
/getWaterByPailNo
/waterEndNotice
/logistics/notify
```

内部服务调用使用：

```text
/internal/**
```

## 6. 第一阶段后端范围

第一阶段只补订单主链路后台 API：

```text
GET  /api/admin/orders
GET  /api/admin/orders/{orderNo}
GET  /api/admin/orders/{orderNo}/progress
POST /api/admin/orders/{orderNo}/lock
POST /api/admin/orders/{orderNo}/unlock
POST /api/admin/orders/{orderNo}/remark
POST /api/admin/orders/{orderNo}/review
POST /api/admin/orders/{orderNo}/dispense
POST /api/admin/orders/{orderNo}/recheck
POST /api/admin/orders/{orderNo}/address
```

接口必须返回：

- 业务状态。
- 中文状态名称。
- 操作人。
- 操作时间。
- 状态流转日志。
- 失败原因。

链路追踪由 SkyWalking 负责，不把链路追踪 ID 作为 API 业务字段返回。

## 7. 状态模型

| 旧状态码 | 旧语义 | 新状态建议 |
| --- | --- | --- |
| `5` | 待审核 | `PENDING_REVIEW` |
| `15` | 审核通过/待调剂 | `REVIEWED` |
| `20` | 已复核/待煎煮 | `RECHECKED` |
| `30` | 已打包 | `PACKED` |
| `40` | 已签收 | `SIGNED` |
| `98` | 已取消 | `CANCELLED` |
| `99` | 已作废 | `VOIDED` |

状态推进必须由应用服务或状态机统一处理，不允许业务代码分散更新订单状态。

状态更新必须带条件更新或乐观锁，避免审方、调剂、复核、煎煮、物流等操作并发覆盖状态。

## 8. 领域建模原则

- Controller 只做协议适配。
- Application Service 编排用例、事务和跨服务调用。
- Domain 承载状态机和业务规则。
- Infrastructure 承载 MyBatis-Plus Mapper、MyBatis XML、HTTP、MQ、缓存和外部协议适配。
- `zhyf-common` 不放具体业务规则。
- 外部旧协议通过 adapter 转换到内部命令对象。

## 9. 兼容策略

外部接口兼容分三种方式：

1. gateway 直接转发到新服务。
2. 新服务提供 legacy controller，路径和入参兼容旧接口。
3. 对字段差异较大的接口，增加 adapter，把旧报文转换成新命令。

不建议直接复制老 Controller。老 Controller 过大，且混合页面模型、业务判断、返回视图，不适合作为新架构基础。

## 10. 验收标准

- 后台订单主链路接口可以被前端完整调用。
- 外部下单后，后台订单列表可见。
- 审方、调剂、复核状态能正确推进。
- 状态推进写入 `order_status_log`。
- 操作失败返回明确业务原因。
- 关键接口能在 SkyWalking 中看到链路。
- Prometheus 能采集服务健康和 JVM 指标。
- Maven 构建和相关测试通过。

# 前端架构重构方案

## 1. 方案结论

`admin-web` 需要进行一次架构级前端整改，但不需要推倒重写业务系统。

本次重构应保留已经验证的 Vue 3、TypeScript、Vite、Vue Router、管理端认证、API 客户端、领域格式化函数和大部分页面业务逻辑，重点替换以下部分：

- 手工导入并同时挂载全部页面的根组件结构。
- 多轮追加形成的全局样式覆盖链。
- 与老后台操作习惯偏离的浅色卡片式应用壳层。
- 页面各自维护的筛选、表格、分页、弹窗和状态反馈样式。
- 仅有路由入口、但缺少独立页面结构和完整状态的聚合页面。

目标不是逐像素复制 JSP、EasyUI、Bootstrap 和 iframe，而是保留老系统已经被业务人员熟悉的信息架构、操作顺序和信息密度，用现代 Vue 组件、真实路由、权限控制和可维护样式重新实现。

## 3. 老项目中应继承的设计

### 3.1 信息架构

老后台提供 11 个一级菜单和 68 个业务入口，主框架为：

```text
后台主框架
├── 48px 顶栏：系统名称、当前用户、账号操作
├── 200px 左侧导航：一级分组、二级菜单
├── 顶部工作页签：同时保留多个工作页面
└── 中央工作区：筛选、表格、详情和业务动作
```

新前端应继续保留“顶栏 + 左侧分组菜单 + 可关闭页签 + 中央工作区”，使用 Vue Router 和受控页面缓存替代 iframe。

### 3.2 页面操作骨架

老系统主体是高频运营和生产作业页面，核心页面顺序稳定：

```text
页面标题与主要操作
→ 紧凑横向筛选
→ 数据表格或任务列表
→ 行内操作
→ 统计信息与分页
→ 详情、编辑或作业弹层
```

需要继承的业务价值：

- 高密度、低留白、列表优先。
- 筛选项贴近业务字段，查询按钮紧跟筛选项。
- 行内动作靠近当前数据，不让用户在页面上下往返。
- 详情按订单、处方、药品、配送、金额和操作留痕分段。
- 多页面并行处理时保留页签和页面状态。
- 打印、导入、导出和高风险操作有明确结果反馈。

### 3.3 页面类型

新项目需覆盖老项目已有的八类页面结构，而不是用一种卡片页面套全部业务：

| 页面类型 | 老项目特征 | 新项目承载方式 |
| --- | --- | --- |
| 列表/工作台 | 筛选、表格、分页、行内动作 | 标准列表页组件 |
| 新增/编辑 | 单列或双列表单 | Dialog 或 Drawer |
| 详情/操作 | 多段业务信息和动作 | 独立详情路由或右侧 Drawer |
| 导入 | 模板、文件、预检、结果 | 分步导入 Dialog |
| 打印 | 固定纸张、二维码、条码 | 独立打印工作台 |
| 报表 | 时间/机构筛选、汇总、钻取 | 统计列表和明细子路由 |
| 状态反馈 | 空、错、无权限、成功 | 统一反馈组件 |
| 生产大屏 | 深色全屏、图表和实时状态 | 独立全屏路由，不套后台壳层 |

### 3.4 不应继承的技术债

- iframe 页面承载和跨窗口 DOM 调用。
- 固定分辨率、绝对定位和大量固定宽度。
- HTML 表格承担表单和详情布局。
- 页面内联样式、重复 DOM id 和非语义表单。
- Bootstrap、EasyUI、自定义 CSS 多套视觉规则混用。
- 直接依赖本机 Lodop 调用而没有任务状态和失败反馈。

## 4. 当前前端事实与问题

### 4.1 可保留基础

- Vue 3、TypeScript、Vite 和 Vue Router 已投入使用。
- `api/` 已形成统一请求入口、认证刷新和错误处理。
- `domain/` 已集中状态、格式化、CSV 和下载逻辑。
- 管理端登录、刷新令牌、退出、权限过滤和强制下线已经接通。
- `views.ts` 已登记当前 73 个路由入口，包括 4 个新系统独立入口、老系统 68 个业务入口和新增的“机构应用配置”。
- 多数功能页已经包含真实查询或操作逻辑，可迁移而不是全部重写。

### 4.2 架构问题

| 问题 | 当前证据 | 影响 |
| --- | --- | --- |
| 根组件承担路由出口 | `App.vue` 约 1429 行、直接导入 72 个页面组件 | 页面边界不清，首包大，路由和渲染状态容易冲突 |
| 两套页面条件链并存 | 38 个 `v-show` 挂载和 29 个条件分支 | 已出现真实页面与 `PendingMenuPage` 同时显示 |
| 全局 CSS 多轮叠加 | `base.css` 约 4881 行、5 个 `:root` | 选择器相互覆盖，无法判断最终视觉来源 |
| 页面仍依赖旧式类名 | 70 个功能页中 68 个使用 `legacy-*` | “旧式兼容层”已经变成主样式体系 |
| 原生表格重复实现 | 66 个功能页自行输出 `<table>` | 列宽、空态、加载、分页和移动端行为不一致 |
| TDesign 接入不完整 | 功能页基本未使用 TDesign 组件 | 文档所述组件体系与实际代码不一致 |
| 路由注册表承担过多职责 | `views.ts` 同时保存路由、菜单、文案、计划和 API 说明 | 文件持续膨胀，运行配置与项目计划耦合 |
| 聚合工作区复用过度 | 多个不同二级菜单映射到同一 `componentKey` | 路由存在，但页面字段、动作和状态未独立验收 |

### 4.3 运行时问题

- 角色管理页运行时高度约 4307px，29 项权限被放入狭窄右栏，难以扫描和保存。
- 390px 宽度下侧栏最大高度 300px，只能看到前部一级菜单，后续业务入口不可达。
- 工号和角色页面同时显示真实页面与“未挂载页面组件”占位内容。
- 业务侧栏展示 `order-service :18082` 等内部服务端口，与业务操作无关。
- 登录页是灰色背景的通用居中表单，与老项目和药房业务缺少视觉关联。
- 管理员显示名在数据库中已是 `?????`，属于数据问题，不能用 CSS 掩盖。
- 当前构建成功只能证明类型和打包通过，不能证明页面布局、路由出口和操作路径正确。

## 5. 重构目标与边界

### 5.1 产品目标

帮助运营人员、审核人员、调剂/复核人员、煎煮中心人员和管理员在高密度桌面工作环境中快速完成查询、判断和操作，同时让查询和只读详情在平板或手机上可用。

### 5.2 核心目标

1. 恢复老系统的信息架构、菜单顺序和高频操作路径。
2. 每个路由只渲染一个页面，页面由路由懒加载决定。
3. 建立唯一设计令牌和公共页面组件，不再靠全局覆盖修补差异。
4. 统一列表、详情、表单、权限、导入、打印和报表页面结构。
5. 保留真实 API、认证、权限和业务动作，不做静态演示页面。
6. 补齐加载、空数据、错误、无权限、只读、禁用、提交中和长内容状态。
7. 让 1366/1440px 桌面作业成为第一优先，同时保证移动端导航和查询可用。

### 5.3 保留范围

- `api/` 的请求契约、刷新令牌和错误模型。
- `domain/` 的中文状态、格式化、CSV 和下载逻辑。
- 已验证的后端接口、权限编码、租户范围和会话机制。
- `views.ts` 中已经确认的菜单名称、顺序、旧路由映射和权限要求。
- 功能页面中已接通的查询、提交、导出和业务状态逻辑。

### 5.4 替换范围

- `App.vue` 的页面组件总装和手工条件渲染。
- `AppLayout.vue` 的浅色壳层、服务端口面板和移动端侧栏方式。
- `base.css` 的多主题叠加和全局页面细节覆盖。
- 页面各自复制的筛选、表格、分页、弹窗和反馈样式。
- 角色权限等不适合常驻分栏的编辑布局。

### 5.5 本方案不包含

- 重写后端接口或改变数据库结构。
- 在方案阶段修改业务状态机。
- 原样迁移 JSP、EasyUI、Bootstrap 或 Lodop 代码。
- 将所有复杂生产操作强行适配为手机端可编辑。
- 把规划中的菜单描述为已经完成的页面。

- `768px - 1199px`：侧栏可折叠，筛选栏允许换行，表格受控横向滚动。
- `>= 1200px`：保持完整侧栏和高密度工作区。
- 移动端保留查询、查看详情、审批结果查看等能力。
- 调剂打印、多桶复核、标签设计和复杂批量配置明确提示“请在桌面端操作”，不提供不可用的压缩版控件。

## 8. 路由与页签设计

### 8.1 路由模块

目标结构：

```text
src/app/router
├── index.ts
├── route-meta.ts
└── modules
    ├── system.ts
    ├── settings.ts
    ├── institutions.ts
    ├── orders.ts
    ├── logistics.ts
    ├── operations.ts
    ├── labels.ts
    ├── sms.ts
    ├── drugs.ts
    ├── reports.ts
    └── decoction.ts
```

每条路由至少包含：

```ts
interface AdminRouteMeta {
  title: string;
  menuGroup: string;
  permission?: string;
  legacyRoute?: string;
  keepAlive?: boolean;
  desktopOnly?: boolean;
  hidden?: boolean;
}
```

页面组件使用动态导入：

```ts
component: () => import('../../features/orders/PrescriptionOrderList.vue')
```

### 8.2 路由规则

- 一个菜单入口对应一个页面路由，不再通过 `componentKey` 手工选择页面。
- 详情页使用 `/resource/:businessKey` 子路由，不以数据库 UUID 作为用户主入口。
- 编辑操作优先使用 Dialog/Drawer；需要分享、刷新恢复或复杂工作流时使用独立子路由。
- 未实现路由不得标记 `implemented: true`；导航可以显示“建设中”，但不能渲染开发元数据占位页给业务用户。
- 404、403、无权限和接口不可用分别处理，不统一重定向到工作台掩盖问题。

### 8.3 页签与缓存

- 页签键使用规范化 `fullPath`，同一业务详情可按业务编号区分。
- 关闭页签后选择相邻页签；首页不可关闭。
- 页面缓存使用路由 `keepAlive` 白名单，不默认缓存所有页面。
- 查询条件优先同步到 URL query；返回列表时恢复筛选、页码和滚动位置。
- 登出、强制下线和权限变化后清空页签缓存，避免保留越权页面。

### 8.4 菜单与权限

- `views.ts` 拆分为运行时菜单、路由配置和项目实施矩阵，运行时代码不保存计划说明。
- 菜单按后端权限编码过滤，按钮权限在页面内二次判断。
- 当前账号无权访问的路由返回 403 页面，不展示空白或直接跳首页。
- 角色、机构范围变化造成会话失效后，统一回到登录页并提示原因。

| `ExportAction` | 同步/异步导出状态和下载 |
| `PermissionGuard` | 页面和按钮权限控制 |
| `PageState` | 加载、空、错、403、只读状态 |

TDesign 用于表单、表格、Dialog、Drawer、Tabs、Tree、Pagination、Dropdown 和反馈组件。业务组件负责字段、流程和状态，不直接重新实现基础交互。

### 9.3 状态管理

第一阶段不强制新增全局状态库，使用类型化 composable 管理：

- `useAdminSession`：登录会话和权限。
- `useWorkspaceTabs`：页签、缓存和关闭策略。
- `useRouteQuery`：筛选、页码和 URL 同步。
- `useAsyncPage`：加载、错误、重试和并发取消。
- `useConfirmAction`：高风险确认和提交锁。

当跨页面共享状态明显增多时再评估 Pinia，不能为了重构形式先引入空壳状态库。

## 10. 标准页面模式

### 10.1 列表页

```text
ListPage
├── PageHeader
│   └── PrimaryActions
├── SearchToolbar
├── BatchActionBar（有选中项时显示）
├── DataTable
│   └── RowActions
└── TablePagination
```

- 桌面筛选横向排列，超过首行的低频条件可折叠。
- 表格头固定仅在长列表确有需要时启用。
- 行内默认显示一至三个高频动作，其余进入菜单。
- 表格下方左侧显示统计，右侧分页。

### 10.2 配置 CRUD 页

```text
ConfigurationPage
├── PageHeader
├── SearchToolbar
├── DataTable
└── FormDialog / FormDrawer
```

保存成功后关闭弹层、刷新原列表并保留筛选条件；保存失败时保留用户输入。

### 10.3 订单详情与业务工作台

```text
OrderWorkspace
├── OrderSummaryBar
├── StickyActionBar
├── OrderBasicSection
├── PrescriptionSection[]
│   ├── PatientAndDiagnosis
│   ├── HerbTable
│   └── PrescriptionAmounts
├── DeliverySection
├── WorkflowTimeline
└── OperationAudit
```

- 不把订单、处方、药品和日志压入一张无限横向表格。
- 审核、调剂、复核分别有独立动作区和状态约束。
- 高风险动作必须显示当前状态、影响结果、原因字段和提交中状态。

### 10.4 角色与权限页

```text
RoleManagementPage
├── PageHeader
├── SearchToolbar
├── RoleTable
└── RoleAuthorizationDrawer
    ├── RoleForm
    ├── PermissionTree
    ├── InstitutionScopeSelector
    └── StickyFooterActions
```

权限树在 Drawer 内按领域分组，支持全选、半选、搜索和固定底部保存栏。主页面不常驻狭窄右栏，不显示权限编码作为主要信息。

### 10.5 导入页

```text
ImportWizard
├── TemplateDownload
├── FileSelection
├── ValidationPreview
├── ConfirmImport
└── ImportResult
```

导入必须区分文件未选、格式错误、预检失败、部分失败、全部成功；错误明细可以下载。

### 10.6 打印页

```text
PrintWorkspace
├── BusinessQuery
├── PrinterAndTemplateSelector
├── FixedSizePreview
├── PrintAction
└── PrintTaskHistory
```

处方、物流面单和标签使用固定毫米尺寸预览，不随普通响应式容器缩放；打印结果、失败原因、重试和重打原因需要留痕。

### 10.7 报表页

```text
ReportPage
├── ReportFilters
├── SummaryTable
├── DrillDownLink
├── DetailTable
└── ExportAction
```

统计与明细保持独立路由关系；金额、剂量、数量和时间统一格式化，大范围查询转异步导出。

## 11. 交互与状态要求

每个迁移页面必须实际实现以下状态：

| 状态 | 要求 |
| --- | --- |
| 加载 | 保持表格和表单结构稳定，避免页面跳动 |
| 空数据 | 说明当前筛选无结果，提供清空筛选或新增动作 |
| 接口错误 | 展示业务提示和重试，不直接暴露异常堆栈 |
| 无权限 | 403 页面或禁用动作，并说明权限不足 |
| 只读 | 仍可查看数据，编辑控件和提交动作明确禁用 |
| 提交中 | 锁定重复提交，按钮显示进行中 |
| 长内容 | 名称、地址和备注可换行或展开，不能覆盖相邻内容 |
| 批量操作 | 显示选中数量、影响范围、成功和失败明细 |
| 高风险操作 | 二次确认、原因、权限、状态校验和审计 |

页面不得用“刷新成功”覆盖真实错误，也不得在失败后清空用户尚未保存的输入。

## 12. API 与数据边界

- 页面只调用 gateway 暴露的管理端 API，不直接连接内部服务端口。
- API 类型继续放在 `api/types.ts` 或按领域拆分的类型文件，禁止使用 `any`。
- 分页结构在 API 适配层统一，不让页面重复转换 `items/records` 差异。
- 后端返回的中文 `statusLabel` 优先；前端领域映射只做兼容兜底。
- 主界面展示机构名、订单号、处方号、患者名和中文业务状态；UUID 和技术编码放在详情或诊断区。
- 查询请求支持取消或忽略过期响应，防止快速筛选时旧结果覆盖新结果。
- 登录和刷新失败统一清理会话；权限变更后不得继续显示缓存中的受限数据。

## 13. CSS 与组件迁移策略

### 13.1 目标规则

- 只保留一个 `:root` 设计令牌入口。
- 全局 CSS 只负责令牌、重置、壳层和少量工具类。
- 页面样式使用 scoped CSS 或领域组件样式，不用高权重全局选择器覆盖所有表格。
- 不再新增 `legacy-*` 类；已迁移页面删除对应旧类依赖。
- 不使用 `!important` 处理正常层级冲突，打印样式等明确例外需说明原因。
- 不把页面区块都包装成卡片，主要通过边框、背景和间距建立层级。

### 13.2 过渡方式

重构期间允许未迁移页面继续使用旧样式，但必须满足：

1. 新壳层样式有独立作用域，不再向 `base.css` 追加覆盖补丁。
2. 每迁移一个页面，同时删除该页面依赖的旧式选择器。
3. 迁移批次结束时统计剩余 `legacy-*` 使用文件。
4. 最后一个页面迁移完成后删除兼容层，不永久保留双设计系统。

## 14. 实施顺序

### 阶段 0：建立可回归基线

- 固定当前 73 个路由、权限和核心动作清单。
- 保存登录、工作台、处方列表、角色、工号、订单详情的桌面/移动截图。
- 建立路由巡检脚本，记录 HTTP、控制台错误、页面错误和水平溢出。
- 记录当前业务可用路径，重构不得让已接通动作回退。

验收：基线可重复执行，截图和路由清单不包含密码、令牌或患者敏感数据。

### 阶段 1：修复根组件和应用壳层

- 将页面挂载迁移到 RouterView 和懒加载路由。
- 删除真实页面与 `PendingMenuPage` 重复渲染路径。
- 重构深色顶栏、200px 导航、工作页签和移动 Drawer。
- 移除侧栏内部服务端口。
- 完成登录页视觉重构和账号菜单。
- 修复管理员显示名数据后再验收顶栏，不用前端硬编码替代。

验收：任一路由只有一个主页面；移动端可访问全部菜单；刷新和页签恢复正确。

### 阶段 2：建立公共页面组件

- 落地令牌、TDesign 适配、PageHeader、SearchToolbar、DataTable、Pagination 和 PageState。
- 建立 Dialog、Drawer、确认、导入和导出公共行为。
- 先迁移工作台、用户/工号、角色、菜单和参数管理作为样板。

验收：角色授权不再形成超长右栏；系统/参数页共享同一列表和表单规范。

### 阶段 3：迁移机构、药品和基础配置

- 迁移机构、机构应用、白名单、接口权限。
- 迁移药品、药品索引、区域、导入和操作日志。
- 对安全配置和导入动作补齐确认、预检、结果和审计反馈。

验收：列表字段和老系统审查矩阵一致，密钥和系统 ID 不进入主信息区。

### 阶段 4：迁移订单与工作流

- 迁移处方列表、订单详情、审核、调剂、复核和多桶复核。
- 迁移地址修改、处方修改、订单操作、重打、仓库、拦截、走流程和签收。
- 建立订单详情分段和固定操作栏。

验收：以真实订单跑通查询、详情、审核、调剂、复核和状态回显；并发和重复提交行为不回退。

### 阶段 5：迁移物流、煎煮、标签和短信

- 区分物流查询、物流作业、规则配置和打印工作台。
- 区分煎煮设备配置、生产作业和云打印记录。
- 建立固定尺寸标签/面单预览和打印任务结果。
- 补齐短信模板、单发、批量发送和发送记录状态。

验收：打印尺寸、失败重试、重打原因和生产动作在桌面端完整可用。

### 阶段 6：迁移报表、维护和运维入口

- 迁移 16 个独立报表入口及汇总到明细钻取。
- 迁移订单流程、异常日志、MQ、问题件和系统健康页面。
- 技术字段只在诊断区展示，业务列表优先显示阶段、原因和恢复动作。

验收：大查询受时间范围或异步任务约束；重放和补偿动作具备权限、确认和审计。

### 阶段 7：删除兼容层

- 删除未使用的 `legacy-*` 样式和旧页面挂载代码。
- 将 `base.css` 收敛为令牌、重置和壳层入口。
- 复核全部路由、权限、移动导航和构建产物。

验收：只剩一套主题令牌和一套页面组件规范，不存在双壳层或重复页面出口。

## 16. 风险与修正

| 风险 | 修正措施 |
| --- | --- |
| 只换颜色，没有解决结构问题 | 阶段 1 先替换路由出口和壳层，再迁移视觉 |
| 为追求一致性丢失真实业务动作 | 每批以当前可用路径和功能矩阵做回归 |
| 同时重写 70 个页面导致长期不可发布 | 按领域分批迁移，每批可独立上线和回滚 |
| 公共组件过度抽象 | 先从三类真实页面提取，禁止为单页建立通用框架 |
| TDesign 默认样式再次与业务密度冲突 | 通过唯一令牌和适配层统一尺寸，不在页面重复覆盖 |
| 移动端变成压缩桌面表格 | 查询/查看专门设计，复杂生产动作明确桌面限制 |
| 页签缓存保留过期权限数据 | 登出、强制下线和权限变化时清空缓存 |
| 旧样式兼容层永久存在 | 每批记录删除数量，阶段 7 作为交付阻断项 |
| 视觉截图没有真实业务内容 | 使用脱敏开发数据覆盖长名称、空值和异常状态 |
| 仅以构建成功宣告完成 | 强制执行路由、截图、交互、权限和控制台验收 |

## 17. 验证方案

### 17.1 自动验证

- `npm run build`：类型检查和生产构建。
- 路由巡检：当前 73 个路由逐个访问，验证页面标题、权限结果和唯一主页面。
- 控制台检查：无 `console.error`、未捕获异常和资源 404。
- DOM 检查：页面内不存在同时可见的真实页面和占位页面。
- 溢出检查：壳层无非预期水平滚动，表格滚动限制在表格容器内。

### 17.2 视觉验证

每批至少检查以下宽度：

| 宽度 | 目的 |
| ---: | --- |
| 1440px | 主要运营桌面 |
| 1366px | 常见生产电脑 |
| 768px | 平板和窄桌面 |
| 390px | 移动查询和导航 |

关键截图：登录、工作台、处方列表、订单详情、审核、调剂、复核、工号、角色授权、机构权限、导入、打印、报表和异常处理。

### 17.3 交互验证

- 菜单展开、折叠和移动 Drawer。
- 页签打开、切换、关闭、刷新恢复和登出清理。
- 查询、重置、分页、长字段和空结果。
- 新增、编辑、保存失败、取消和脏数据保护。
- 无权限、只读、禁用和强制下线。
- 批量操作、导入预检、导出任务和打印结果。
- 审核、调剂、复核等状态推进的重复提交保护。

## 18. 发布与回滚

- 每个实施阶段独立提交、构建、截图和开发环境验收。
- 不在一个发布中同时替换全部页面。
- 新壳层发布前保留上一版前端镜像或静态目录。
- 页面迁移出现阻断时回滚该批前端镜像；API 和数据库不因纯前端迁移回滚。
- 删除旧样式前先确认该批页面没有 `legacy-*` 依赖。
- 视觉和交互验收通过后再进入下一批，不以“后续统一调整”跨批遗留明显问题。

## 19. 完成标准

前端重构只有同时满足以下条件才可声明完成：

1. 73 个当前路由均有明确的完成、建设中或无权限状态。
2. 每个路由只渲染一个主页面，没有占位页叠加。
3. 11 个一级菜单和老系统 68 个业务入口顺序、粒度和操作路径完成核对。
4. 登录、顶栏、侧栏、页签和工作区形成统一视觉体系。
5. 列表、详情、表单、导入、打印、报表和反馈页面使用统一组件模式。
6. 只保留一套设计令牌，不再通过多个 `:root` 和全局覆盖维持页面。
7. 所有关键页面具备加载、空、错、403、只读、禁用和提交中状态。
8. 1440、1366、768、390 四种宽度完成截图和溢出检查。
9. 认证、权限、租户范围、刷新令牌和强制下线行为没有回退。
10. `npm run build`、路由巡检、控制台检查和真实业务链路验收全部通过。

本方案是后续前端代码整改的实施基线。具体页面字段、动作和 API 验收继续以 `../功能方案/前端功能方案.md` 的菜单矩阵为准。

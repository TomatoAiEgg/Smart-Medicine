# 事务一致性设计

## 1. 设计目标

智能药房链路涉及外部下单、订单落库、审方、调剂、复核、煎煮、物流、回调、报表和运维补偿。该链路跨多个服务和外部系统，不适合用全局强事务硬串起来。

本系统事务目标：

- 单服务内使用本地数据库事务保证强一致。
- 跨服务使用 Outbox + RocketMQ + 幂等 + 重试 + 补偿保证最终一致。
- 所有状态推进必须可审计、可追踪、可人工补偿。
- 外部系统调用失败不能破坏已提交的内部业务事实。

## 2. 事务边界

### 2.1 本地事务

同一个服务、同一个数据库内的强一致操作必须放在一个本地事务里。

订单创建：

```text
order-service 本地事务
 -> order_main
 -> prescription
 -> prescription_detail
 -> order_status_log
 -> event_outbox
```

审方通过：

```text
workflow-service 本地事务
 -> workflow_task 审方任务完成
 -> prescription_audit_record
 -> operation_log
 -> event_outbox
```

调剂完成：

```text
workflow-service 本地事务
 -> workflow_task 调剂任务完成
 -> prescription_dispense_record
 -> workflow_task 生成复核任务
 -> operation_log
 -> event_outbox
```

复核完成：

```text
workflow-service 本地事务
 -> workflow_task 复核任务完成
 -> prescription_recheck_record
 -> operation_log
 -> event_outbox
```

物流发货：

```text
logistics-service 本地事务
 -> shipment
 -> shipment_trace
 -> operation_log
 -> event_outbox
```

### 2.2 跨服务事务

跨服务不使用 2PC 或 XA 作为默认方案。

原因：

- 链路长，涉及订单、流程、煎煮、物流、回调和外部系统。
- 外部系统不可控，强事务无法覆盖真实回调和网络失败。
- 强事务会增加锁等待、超时和整体耦合。

跨服务统一使用最终一致：

```text
业务服务本地事务写业务表和 event_outbox
 -> message-service 扫描 Outbox
 -> RocketMQ 发布事件
 -> 消费服务幂等处理
 -> 失败重试
 -> 超过阈值进入 DEAD 或人工补偿
```

## 3. Outbox 规则

业务状态变更后需要通知其他服务时，必须在同一个本地事务内写 `event_outbox`。

规则：

- 业务表和 `event_outbox` 必须同事务提交。
- `event_outbox.event_id` 全局唯一。
- 事件只描述已经发生的事实，不承载复杂业务判断。
- `message-service` 负责扫描、发布、标记发送状态。
- 发送失败按重试策略推进，不回滚已提交业务表。

典型事件：

| 事件 | 来源服务 | 消费方 |
| --- | --- | --- |
| `ORDER_CREATED` | `order-service` | `message-service`、`workflow-service` |
| `ORDER_REVIEWED` | `workflow-service` | `callback-service`、`ops-service` |
| `PRESCRIPTION_DISPENSED` | `workflow-service` | `workflow-service`、`ops-service` |
| `PRESCRIPTION_RECHECKED` | `workflow-service` | `decoction-service`、`callback-service` |
| `DECOCTION_FINISHED` | `decoction-service` | `logistics-service`、`callback-service` |
| `LOGISTICS_SHIPPED` | `logistics-service` | `callback-service`、`ops-service` |

## 4. 幂等设计

所有外部入口、人工操作和 MQ 消费必须有幂等键。

| 场景 | 幂等键 |
| --- | --- |
| 外部下单 | `tenantId + institutionId + externalOrderNo` |
| 外部取消订单 | `tenantId + institutionId + externalOrderNo + action` |
| 更新地址 | `tenantId + institutionId + externalOrderNo + addressVersion/actionTime` |
| 审方动作 | `taskId + action` |
| 调剂动作 | `taskId + action` |
| 复核动作 | `taskId + action` |
| PDA/MES 操作 | `operationId` |
| 物流轨迹回调 | `logisticsNo + traceStatus + traceTime` |
| 机构状态回调 | `callbackType + businessId` |
| MQ 消费 | `consumerGroup + eventId` |

实现要求：

- 唯一索引优先于纯代码判断。
- 重复请求如果业务结果已成功，应返回幂等成功。
- 重复请求如果上次失败且允许重试，应进入重试逻辑。
- 状态不一致的重复请求必须返回明确业务错误。

## 5. 状态机和并发控制

订单、处方、流程任务、煎煮任务、物流单都必须由状态机控制。

状态更新必须使用条件更新或乐观锁：

```sql
update order_main
set status = ?, version = version + 1, updated_at = now()
where id = ?
  and status = ?
  and version = ?
```

更新行数为 0 时，说明：

- 当前状态已被其他操作推进。
- 当前版本已过期。
- 当前动作不再允许执行。

处理方式：

- 查询最新状态。
- 如果最新状态已经等于目标结果，按幂等成功处理。
- 如果最新状态不允许当前动作，返回业务错误。
- 不允许直接覆盖最新状态。

## 6. 失败和补偿

### 6.1 事务内失败

本地事务内任一关键写入失败，整个事务回滚。

例子：

- 订单写入成功但处方明细写入失败：回滚订单。
- 审方任务完成但审方记录写入失败：回滚审方任务。
- 调剂记录写入成功但复核任务创建失败：回滚调剂。

### 6.2 事务后失败

本地事务已经提交后，不能再回滚业务事实，只能补偿。

例子：

- 订单已创建但 MQ 未发出：Outbox 继续重试。
- 复核完成但煎煮服务消费失败：消息消费重试，失败进入运维补偿。
- 物流已发货但机构回调失败：`callback_record` 重试，超过阈值进入人工处理。
- MES 已通知煎煮完成但订单状态推进失败：记录失败事件，进入运维补偿。

### 6.3 人工补偿入口

`ops-service` 需要提供：

- Outbox 积压查询。
- MQ 消费失败查询。
- 回调失败查询。
- 煎煮事件失败查询。
- 订单状态日志查询。
- 人工重试。
- 标记已处理。
- 问题件登记。

## 7. 数据库约束

建议约束：

- `order_main`：`tenant_id + institution_id + external_order_no` 唯一。
- `prescription`：`tenant_id + institution_id + external_prescription_no` 唯一。
- `event_outbox`：`event_id` 唯一。
- `message_consume_log`：`consumer_group + event_id` 唯一。
- `workflow_task`：同一来源事件和任务类型唯一。
- `callback_record`：`callback_type + business_id` 唯一。
- PDA/MES 操作记录：`operation_id` 唯一。

## 8. Spring 事务落地

后端使用 Spring 声明式事务：

- Application Service 方法作为事务边界。
- Repository 只做数据访问，不开启事务。
- 外部 HTTP 调用不放在数据库事务中。
- MQ 发布不放在业务事务中，业务事务只写 Outbox。
- 批量导入分批提交，避免长事务。

示例边界：

```text
Controller
 -> ApplicationService @Transactional
    -> Domain 状态机校验
    -> Repository 写业务表
    -> Repository 写状态日志
    -> Repository 写 event_outbox
 -> 返回业务结果
```

## 9. 前端事务感知

前端不直接处理事务，但需要正确处理事务结果：

- 操作中：按钮 loading，防止重复点击。
- 操作成功：刷新列表和详情。
- 操作失败：展示后端业务提示。
- 已被他人处理：提示状态已变化，刷新页面。
- 当前状态不允许操作：禁用按钮或展示原因。
- 后台处理中：提示稍后刷新，不伪造最终状态。

前端不要因为接口返回慢而本地强行改状态，最终显示以服务端查询结果为准。

## 10. 验收标准

- 创建订单时，订单、处方、明细和 Outbox 要么全部成功，要么全部回滚。
- 审方、调剂、复核任务状态和操作记录同事务提交。
- 重复下单不会产生重复订单。
- 重复消费不会重复推进状态。
- 并发操作同一任务时只有一个成功。
- 事务后外部失败能通过 Outbox、重试或人工补偿恢复。
- SkyWalking 能看到跨服务链路，日志能按订单号和事件 ID 对齐。

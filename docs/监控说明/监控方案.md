# 监控方案

## 1. 监控目标

监控目标覆盖四类问题：

- 服务是否存活。
- 接口是否慢或失败。
- SQL 是否慢、锁等待或连接池耗尽。
- 订单主链路是否断在某个环节。

当前监控部署目标主机：

```text
47.120.55.53
```

## 2. 服务监控

每个 Java 服务需要开启 actuator：

```text
/actuator/health
/actuator/metrics
/actuator/prometheus
```

Prometheus 采集指标：

- JVM 内存。
- JVM GC。
- 线程数。
- HTTP 请求耗时。
- HTTP 请求错误率。
- 数据库连接池。
- RocketMQ 生产和消费指标。
- 自定义业务指标。

Grafana 看板：

- 服务健康总览。
- JVM 总览。
- HTTP 接口总览。
- 数据库连接池。
- 订单主链路业务指标。
- 容器 CPU、内存、磁盘、网络。

## 3. SQL 监控

SQL 监控分三层。

### 3.1 应用层

Spring JDBC、连接池和 Repository 数据访问需要记录：

- 慢 SQL。
- SQL 执行耗时。
- SQL 异常。
- 数据库连接池耗尽。
- 事务失败。

要求：

- 开发和测试环境可以开启 SQL 日志。
- 生产或准生产环境只记录慢 SQL 摘要，不输出敏感参数。
- 报表查询、订单列表、处方详情、流程任务列表必须重点监控。

### 3.2 PostgreSQL 层

关注：

- 连接数。
- 活跃查询。
- 慢查询。
- 锁等待。
- 索引命中率。
- 缓存命中率。
- 磁盘空间。

常用检查：

```sql
select now(), count(*) from pg_stat_activity;
select query, state, wait_event_type, wait_event from pg_stat_activity where state <> 'idle';
select relname, seq_scan, idx_scan from pg_stat_user_tables order by seq_scan desc limit 20;
```

### 3.3 业务 SQL

重点关注：

- 订单列表查询耗时。
- 订单详情查询耗时。
- 审方任务查询耗时。
- 调剂任务查询耗时。
- 复核任务查询耗时。
- 物流待发货查询耗时。
- 报表查询耗时。

这些查询必须配套分页、时间范围和索引。

## 4. 链路追踪

链路追踪使用 SkyWalking，不把链路追踪 ID 作为前后端接口字段。

需要覆盖：

- gateway
- order-service
- message-service
- workflow-service
- decoction-service
- logistics-service
- callback-service
- ops-service

核心链路：

```text
外部下单
 -> gateway
 -> order-service
 -> event_outbox
 -> message-service
 -> RocketMQ
 -> workflow-service
 -> order-service 状态更新
 -> callback-service
```

排查方式：

- 前端记录接口路径、请求时间、订单号、操作人、错误码。
- 后端在 SkyWalking 按时间窗口和 endpoint 查询。
- 服务日志按订单号、处方号、事件 ID、操作人关联。

## 5. 业务监控指标

建议增加业务指标：

- 今日新增订单数。
- 待审方数量。
- 待调剂数量。
- 待复核数量。
- 待煎煮数量。
- 待发货数量。
- 回调失败数量。
- Outbox 待发送数量。
- 消费失败数量。
- 死信数量。
- 已发布但长时间未消费数量。
- Outbox 发布中超时数量。
- MQ 消费追平时间。
- 平均审方耗时。
- 平均调剂耗时。
- 平均复核耗时。
- 平均发货耗时。

## 6. 告警建议

- 服务健康检查失败。
- 接口 5xx 错误率超过阈值。
- P95 接口耗时超过阈值。
- PostgreSQL 连接数接近上限。
- Redis 不可用。
- RocketMQ Broker 不可用。
- Outbox 积压超过阈值。
- Outbox `PUBLISHING` 超时。
- 已发布消息长时间未被核心消费组消费。
- 消费失败持续增加。
- MQ 积压持续增长且无法追平。
- 回调失败持续增加。
- 磁盘使用率超过阈值。

## 7. 压测与容量验证

压测不包装成生产真实高并发，定位为开发测试环境的容量验证和瓶颈演练。

专项方案见：

```text
docs/05_测试压测/压测与容量验证方案.md
```

压测时重点关联：

- k6 或 JMeter 压测结果。
- SkyWalking 接口链路和慢接口。
- Prometheus 服务、JVM、容器和数据库连接池指标。
- Grafana 业务看板和 MQ 积压看板。
- PostgreSQL 慢 SQL 和锁等待。
- RocketMQ Outbox、消费失败、死信和追平时间。

## 8. 消息可靠性和容灾监控

专项方案见：

```text
docs/中间件说明/RocketMQ可靠性与容灾方案.md
```

监控看板需要能直接回答：

- Outbox 有没有生成。
- Outbox 有没有发布成功。
- 发布成功后目标消费组有没有消费。
- 失败消息是否进入重试或死信。
- 未消费超时是否告警。
- 积压恢复后用了多久追平。
- RocketMQ 故障后是否能从 Outbox 补发。

## 9. 日志要求

每条关键日志至少包含：

- service。
- orderNo。
- prescriptionNo。
- eventId。
- operator。
- action。
- result。
- reason。

不要在日志中输出：

- 密码。
- appSecret。
- token。
- 身份证等敏感完整信息。
- 完整生产报文中的敏感字段。

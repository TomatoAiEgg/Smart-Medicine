# 压测与容量验证方案

## 1. 定位

本项目真实业务订单量不高，不包装成生产高并发系统。压测目标是基于真实智能药房业务链路，模拟高于真实流量很多倍的开发测试压力，验证系统在订单创建、审方、调剂、复核、煎煮、物流、回调、消息消费和补偿场景下的稳定性。

压测结论必须基于测试环境数据，不写成生产真实流量。

## 2. 验证目标

- 验证核心接口在并发请求下的响应时间和错误率。
- 验证订单全链路状态推进是否稳定。
- 验证 RocketMQ 积压后是否能自动追平。
- 验证消费幂等、重复提交、并发操作和补偿重放是否正确。
- 验证 PostgreSQL 慢 SQL、连接池、锁等待和索引设计。
- 验证 Redis、RocketMQ、SkyWalking、Prometheus、Grafana 的监控闭环。

## 3. 压测环境

开发测试环境部署在云服务器：

```text
47.120.55.53
```

建议压测时使用独立测试租户、测试机构和测试药品数据，不使用真实生产账号和真实患者信息。

压测前需要确认：

- Nginx、gateway、各 Java 服务正常。
- PostgreSQL、Redis、RocketMQ 正常。
- SkyWalking 可以看到服务拓扑和接口链路。
- Prometheus 可以采集 JVM、HTTP、数据库连接池和容器指标。
- Grafana 看板能看到接口耗时、错误率、CPU、内存、MQ 积压和业务指标。

## 4. 压测工具

第一版建议使用 k6，原因是脚本可版本化、参数化方便、结果容易输出。

JMeter 可作为补充，适合做可视化录制和接口调试，但正式压测脚本建议以 k6 为主。

推荐目录：

```text
tests/performance/
 -> config/
 -> data/
 -> scripts/
 -> reports/
```

## 5. 压测场景

### 5.1 单接口压测

重点接口：

| 场景 | 接口类型 | 观察重点 |
| --- | --- | --- |
| 登录 | 认证接口 | token 发放耗时、错误率 |
| 订单创建 | 写接口 | 本地事务耗时、Outbox 写入、数据库连接池 |
| 订单列表 | 查询接口 | 分页、索引、P95/P99 |
| 订单详情 | 查询接口 | 多表查询耗时 |
| 审方提交 | 状态推进 | 乐观锁、重复提交 |
| 调剂提交 | 状态推进 | 幂等、任务状态 |
| 复核提交 | 状态推进 | 状态机、MQ 事件 |
| 物流发货 | 外部集成 | 回调事件、补偿记录 |
| 人工重放 | 运维接口 | 幂等和审计日志 |

### 5.2 订单全链路压测

模拟完整链路：

```text
创建订单
 -> 生成处方
 -> 审方
 -> 调剂
 -> 复核
 -> 煎煮事件
 -> 物流发货
 -> 机构回调
```

观察重点：

- 订单最终状态是否正确。
- 每个环节是否只推进一次。
- `event_outbox` 是否及时发布。
- RocketMQ 是否积压。
- 消费失败后是否重试。
- 回调失败后是否进入补偿队列。

### 5.3 异常压测

异常场景：

| 场景 | 预期结果 |
| --- | --- |
| 重复提交同一外部订单 | 只生成一笔订单，重复请求返回幂等结果 |
| 两个窗口同时审方 | 只有一次成功，另一次提示状态已变化 |
| 重复点击调剂/复核 | 不重复推进状态，不重复生成任务 |
| 同一 MQ 消息重复投递 | 消费端识别已消费并跳过 |
| callback-service 停止 5 分钟 | 回调失败记录可重试，服务恢复后可追平 |
| RocketMQ 消费者临时异常 | 消息进入重试，不丢失业务事件 |
| 数据库慢查询 | Grafana 和慢 SQL 日志可定位 |
| Redis 临时不可用 | 核心落库链路不丢数据，缓存读取有降级策略 |

## 6. 并发档位

推荐按四档推进：

| 档位 | 并发用户 | 目标 |
| --- | --- | --- |
| 基线 | 20 | 验证脚本、数据和监控链路 |
| 常规 | 50 | 核心接口稳定，错误率低于 1% |
| 压力 | 100 | 允许异步积压，但压测结束后 MQ 能自动追平 |
| 探测 | 200 | 找瓶颈，不承诺稳定指标 |

订单量建议：

```text
30 分钟 1000 笔测试订单
1 小时 3000 到 10000 笔测试订单
```

该量级已经远高于真实生产流量，足够支撑容量验证和简历描述。

## 7. 指标口径

接口指标：

- QPS。
- 平均响应时间。
- P95 响应时间。
- P99 响应时间。
- 4xx/5xx 错误率。
- 超时数量。

JVM 指标：

- CPU。
- 堆内存。
- GC 次数和耗时。
- 线程数。
- Tomcat 线程池。

数据库指标：

- 连接池活跃连接。
- 慢 SQL 数量。
- 锁等待。
- 索引命中率。
- 订单表、处方表、任务表查询耗时。

MQ 指标：

- Outbox 待发布数量。
- 消息发布失败数量。
- Topic 积压数量。
- 消费失败数量。
- 消费耗时。
- 死信数量。

业务指标：

- 创建订单数。
- 审方完成数。
- 调剂完成数。
- 复核完成数。
- 发货完成数。
- 回调成功数。
- 回调失败数。
- 人工补偿数。

## 9. 压测执行流程

### 9.1 压测前

- 确认当前镜像版本和 Git 提交。
- 清理或隔离旧压测数据。
- 准备测试租户、测试机构、测试药品和测试操作员。
- 打开 Grafana 看板。
- 确认 SkyWalking 能看到服务链路。
- 记录数据库初始连接数、慢 SQL 和 MQ 积压。

### 9.2 压测中

- 从 20 并发开始，不直接上高档位。
- 每个档位至少运行 10 到 30 分钟。
- 每次只调整一个变量，例如并发数、消费者实例数或数据库连接池大小。
- 发现错误率持续升高时停止升档，先定位瓶颈。

### 9.3 压测后

- 等待 MQ 积压追平。
- 检查订单最终状态分布。
- 检查失败消息、死信和补偿记录。
- 导出 Grafana 关键截图。
- 导出 k6 汇总结果。
- 记录瓶颈、优化动作和复测结果。

## 10. 瓶颈分析路径

接口慢：

```text
k6 P95/P99
 -> SkyWalking endpoint
 -> 服务日志
 -> 数据库慢 SQL
 -> 连接池和线程池
```

MQ 积压：

```text
Topic 积压
 -> 消费者实例数
 -> 单条消息处理耗时
 -> 消费失败原因
 -> 下游数据库或外部接口耗时
```

数据库压力高：

```text
慢 SQL
 -> explain analyze
 -> 索引命中
 -> 分页和时间范围
 -> 事务范围
 -> 是否需要分区或归档
```

状态不一致：

```text
订单状态
 -> 状态日志
 -> event_outbox
 -> message_consume_log
 -> 业务操作日志
 -> 人工补偿记录
```

## 11. 优化优先级

第一优先级：

- 修复接口错误和业务状态不一致。
- 修复重复提交、重复消费、并发状态推进问题。
- 修复明显慢 SQL 和缺失索引。

第二优先级：

- 调整数据库连接池、Tomcat 线程池和消费者并发。
- 对查询接口增加缓存或查询条件限制。
- 对回调和通知增加异步重试。

第三优先级：

- 日志表、状态表、消息表按时间分区。
- 历史订单冷热归档。
- 读写分离或只读副本。

不作为第一版目标：

- 分库分表。
- 多 MQ 混用。
- 百万级 QPS 宣称。
- 无业务证据的复杂中间件堆叠。

## 12. 验收标准

基线验收：

- 20 并发全链路稳定完成。
- 核心接口无 5xx。
- 订单最终状态正确。
- 无重复订单、重复任务、重复状态推进。
- SkyWalking、Prometheus、Grafana 有完整观测数据。

常规验收：

- 50 并发下核心接口错误率低于 1%。
- 订单创建、审方、调剂、复核链路可持续运行。
- MQ 压测后可自动追平。
- 慢 SQL 可定位并有优化记录。

压力验收：

- 100 并发下允许短暂 MQ 积压。
- 压测停止后积压能恢复到正常水平。
- 失败消息可见、可重试、可人工补偿。
- 监控看板能说明瓶颈位置。

可以描述：


不要描述：

```text

真实每天几十万订单。

上线大规模分库分表。
```

## 15. 当前结论

本项目的压测价值不在于夸大真实生产并发，而在于用真实复杂业务链路构造可复现的容量验证场景。

第一版应该先把 20、50、100 并发的全链路压测跑通，形成监控截图、压测报告、瓶颈分析和优化记录。这样既能证明系统具备扩展能力，也能沉淀真实可讲的高并发处理经验。

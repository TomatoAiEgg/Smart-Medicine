# 日志监控闭环验收说明

## 1. 当前阶段

正式压测前必须先完成日志和监控闭环。批量推单脚本只能提供业务流量，不能替代观测能力。

当前顺序固定为：

```text
1. HIS 测试脚本基础
2. 日志和监控闭环验收
3. 1 单 / 10 单小流量全链路验收
4. 压测
5. 故障演练
6. K8s
```

## 2. 验收目标

日志和监控闭环要能回答这些问题：

- 服务是否全部健康。
- 每个服务是否暴露 `/actuator/prometheus`。
- Prometheus 是否能抓到所有业务服务。
- Grafana 是否可用。
- ops-service 是否能查到 Outbox、消费日志、死信、回调异常、接入日志。
- 跑完一条订单后，是否能按 `orderNo` 或 `externalOrderNo` 聚合订单状态、任务、消息、回调、死信、访问日志。
- 出问题时能否按 `orderNo`、`externalOrderNo`、`eventId`、`callbackId`、`deadLetterId` 定位。

## 3. 基础观测验收

在云服务器宿主机执行：

```bash
python3 test/integration/verify-observability.py \
  --service-host 127.0.0.1 \
  --web-base-url http://127.0.0.1 \
  --prometheus-url http://127.0.0.1:19090 \
  --grafana-url http://127.0.0.1:13000 \
  --report test/reports/observability.json
```

脚本会检查：

- 13 个后端服务 `/actuator/health`。
- 13 个后端服务 `/actuator/prometheus`。
- admin-web `/health`。
- ops-service 运维查询接口。
- Prometheus `/api/v1/targets`。
- Prometheus `up{job="zhyf-services"}`。
- Grafana `/api/health`。

如果服务器暂时没有暴露 Grafana 或 Prometheus，可以临时跳过：

```bash
python3 test/integration/verify-observability.py --skip-prometheus --skip-grafana
```

## 4. 订单观测验收

跑完一条 HIS 创建订单后，执行：

```bash
python3 test/integration/verify-order-observability.py \
  --web-base-url http://127.0.0.1 \
  --order-no ZHYF202607220001 \
  --min-status-logs 1 \
  --min-outbox 1 \
  --report test/reports/order-observability.json
```

如果只有 HIS 外部订单号，也可以执行：

```bash
python3 test/integration/verify-order-observability.py \
  --web-base-url http://127.0.0.1 \
  --external-order-no HIS202607220001 \
  --min-status-logs 1 \
  --min-outbox 1
```

完整全链路验收时建议提高门槛：

```bash
python3 test/integration/verify-order-observability.py \
  --web-base-url http://127.0.0.1 \
  --order-no ZHYF202607220001 \
  --min-status-logs 3 \
  --min-workflow-tasks 1 \
  --min-outbox 1 \
  --min-consume 1 \
  --min-callbacks 1 \
  --min-access-logs 1
```

该脚本调用：

```text
GET /ops-api/api/admin/ops/order-observability?orderNo=xxx
GET /ops-api/api/admin/ops/order-observability?externalOrderNo=xxx
```

接口聚合以下证据：

- `order_main` 订单主记录。
- `order_status_log` 订单状态变化。
- `workflow_task` 审方、调剂、复核任务。
- `event_outbox` 待发布和已发布事件。
- `message_consume_log` 消费幂等和消费结果。
- `dead_letter_record` 死信。
- `order_validation_record` 订单校验记录。
- `callback_record` 回调记录。
- `integration_retry_task` 集成重试记录。
- `operation_log` 后台操作日志。
- `api_access_log` 最近接入日志。

## 5. 通过标准

| 检查项 | 通过标准 |
| --- | --- |
| 服务健康 | 13 个后端全部 `UP` |
| 服务指标 | 13 个后端 `/actuator/prometheus` 可访问 |
| Prometheus | `zhyf-services` targets 全部 up |
| Grafana | `/api/health` 返回可用 |
| 业务健康 | `/ops-api/api/admin/ops/health-overview` 返回 `SUCCESS` |
| 接入日志 | `/ops-api/api/admin/ops/api-access-logs` 返回 `SUCCESS` |
| Outbox | `/ops-api/api/admin/ops/outbox` 返回 `SUCCESS` |
| 消费日志 | `/ops-api/api/admin/ops/message-consume-logs` 返回 `SUCCESS` |
| 死信 | `/ops-api/api/admin/ops/dead-letters` 返回 `SUCCESS` |
| 回调异常 | `/ops-api/api/admin/ops/logistics-callback-issues` 返回 `SUCCESS` |
| 订单观测 | 指定订单能聚合状态日志、Outbox、消费、回调、死信和访问日志 |

## 6. 和全链路脚本配合

先跑基础观测验收：

```bash
python3 test/integration/verify-observability.py
```

再跑 1 单全链路：

```bash
ZHYF_TEST_APP_SECRET=测试密钥 \
python3 test/integration/his-batch-callback.py \
  --mode full-chain \
  --count 1 \
  --concurrency 1 \
  --listen-callbacks \
  --dispatch-callbacks \
  --report test/reports/his-full-chain-1.json
```

最后按脚本报告里的 `orderNo` 再跑订单观测验收：

```bash
python3 test/integration/verify-order-observability.py \
  --order-no 报告里的订单号 \
  --min-status-logs 3 \
  --min-workflow-tasks 1 \
  --min-outbox 1 \
  --min-consume 1 \
  --min-callbacks 1
```

前后对比重点：

- `recentAccessCount` 是否增加。
- Outbox 是否有新增事件。
- 消费日志是否有对应 `eventId`。
- `callback_record` 是否有对应回调记录。
- Prometheus target 是否仍然全 up。
- SkyWalking 是否能看到 gateway 到后端服务链路。

## 7. 不通过处理

| 失败点 | 优先处理 |
| --- | --- |
| health 失败 | 先看容器状态和服务日志 |
| metrics 失败 | 检查 actuator 配置和 micrometer 依赖 |
| Prometheus target down | 检查网络、端口、Prometheus 配置 |
| ops 查询失败 | 检查 ops-service 日志和数据库表结构 |
| 订单观测查不到订单 | 确认创建订单请求是否成功、订单号是否取自脚本报告 |
| 接入日志为空 | 先跑一次 HIS 创建订单，并确认请求经过 gateway |
| 消费日志为空 | 检查 RocketMQ、message-service、workflow-service 消费 |
| 回调记录为空 | 确认全链路脚本是否触发发货、签收和回调派发 |
| 出现开放死信 | 先查 `dead_letter_record`，再决定重放或关闭 |

压测只能在本说明的基础检查和订单观测检查通过后开始。

## 3. 新库设计原则

### 3.1 数据库

新系统继续使用 PostgreSQL，原因：

- 当前新系统 migration 已经基于 PostgreSQL。
- JSONB 适合保存外部原始报文和扩展字段。
- 观测、报表、索引和事务能力满足重构目标。

旧 MySQL 只作为迁移源和字段参考，不作为新系统长期主库。

事务一致性设计详见 [事务一致性设计.md](D:/workspace/包装项目/智能药房SaaS平台/docs/03_架构设计/事务一致性设计.md)。数据库层需要通过唯一约束、状态日志、Outbox 表、消费幂等表和乐观锁版本字段支撑最终一致性。

### 3.2 持久化框架

后端不再继续扩展手写 `JdbcTemplate` 方案，统一改为：

- MyBatis-Plus 作为主持久化框架。
- MyBatis XML 或注解 SQL 承接复杂报表和跨表查询。
- Flyway 继续管理数据库结构变更。
- PostgreSQL JSONB、复杂聚合、批量写入等场景允许保留少量手写 SQL，但必须封装在 Mapper 层，不在 Service 里拼 SQL。

选择 MyBatis-Plus 的原因：

- 老项目本来就是 MyBatis 体系，迁移成本低。
- 比 JPA 更适合旧系统复杂查询、报表、状态流转和遗留字段映射。
- 比手写持久化代码少大量 RowMapper 和重复 CRUD。
- 支持 Spring Boot 3 体系，可以使用 `mybatis-plus-spring-boot3-starter`。

## 8. 变更规则

- 所有结构变更必须走 Flyway。
- MyBatis-Plus Entity 和 Mapper 必须跟 migration 同步。
- 复杂查询写在 Mapper XML，不允许在 Service 里拼 SQL。
- 状态字段变更必须写状态日志。
- 外部原始报文必须保留，但敏感字段要脱敏。
- 生产连接信息不写入仓库。
- 迁移脚本先在测试库跑，抽样对账后再进入正式环境。
- 关键状态表必须保留 `version` 或等价并发控制字段。
- 跨服务事件必须先写 `event_outbox`，再由消息服务发布。

## 3. 新库设计原则

### 3.1 数据库

新系统继续使用 PostgreSQL，原因：

- 当前新系统 migration 已经基于 PostgreSQL。
- JSONB 适合保存外部原始报文和扩展字段。
- 观测、报表、索引和事务能力满足重构目标。

旧 MySQL 只作为迁移源和字段参考，不作为新系统长期主库。

事务一致性设计详见 [事务一致性设计.md](../03_架构设计/事务一致性设计.md)。数据库层需要通过唯一约束、状态日志、Outbox 表、消费幂等表和乐观锁版本字段支撑最终一致性。

### 3.2 持久化框架

当前后端使用 Spring JDBC。数据访问规则如下：

- Flyway 继续作为数据库结构唯一变更入口。
- SQL、参数绑定和 RowMapper 统一封装在基础设施层 Repository，不在 Service 拼 SQL。
- PostgreSQL JSONB、复杂聚合和批量写入允许使用结构化 SQL，但必须有明确 DTO 和测试。
- 优先拆分过大的 Repository、复用分页和类型转换组件，避免继续扩大单文件规模。
- 如后续迁移 MyBatis-Plus，必须先形成专项迁移方案并按完整业务域一次迁移，禁止同一领域长期混用两套持久化体系。

## 8. 变更规则

- 所有结构变更必须走 Flyway。
- Repository、查询 DTO 和返回模型必须跟 migration 同步。
- 复杂查询封装在基础设施层，不允许在 Service 里拼 SQL。
- 状态字段变更必须写状态日志。
- 外部原始报文必须保留，但敏感字段要脱敏。
- 生产连接信息不写入仓库。
- 迁移脚本先在测试库跑，抽样对账后再进入正式环境。
- 关键状态表必须保留 `version` 或等价并发控制字段。
- 跨服务事件必须先写 `event_outbox`，再由消息服务发布。

## 9. 第二阶段数据库改动（V43-V45）

本阶段在保留开发库现有数据的前提下完成增量迁移，不删除旧字段，不把旧项目数据库作为写入目标。

### 9.1 V43 管理端权限与租户范围

- 扩展 `operator_user` 的密码摘要、算法、凭证状态、失败次数、锁定时间、登录时间和乐观锁字段；密码摘要允许为空，用于兼容尚未初始化凭证的存量操作员。
- 新增 `admin_role`、`admin_menu`、`admin_permission`、`admin_user_role`、`admin_role_menu`、`admin_role_permission`，将旧式单一 `role_code` 过渡为规范化 RBAC。
- 新增角色和用户两级机构数据范围表，支持租户内按机构授权。
- 保留 `operator_user.role_code` 作为过渡字段，并将已有非空角色代码迁移到新关系表；新功能不得继续只依赖该字段鉴权。
- 新增 `integration_source_binding`，显式维护外部来源系统与租户/机构的绑定。未配置绑定时只允许通过订单、机构编码或“系统仅存在一个启用租户”进行唯一解析。

### 9.2 V44 并发控制与任务认领

- `callback_record`、`integration_retry_task` 和 `workflow_task` 增加 `claimed_by`、`claimed_at`、`claim_expires_at` 与 `version`。
- callback 使用 `SENDING`，integration 使用 `PROCESSING` 表示已认领；服务通过 PostgreSQL `FOR UPDATE SKIP LOCKED` 原子批量认领，到期租约可重新认领。
- 完成、失败和死亡状态更新必须同时匹配任务 ID、处理中状态和本次认领所有者，过期工作线程不能覆盖后续认领结果。
- `integration_message` 和 `integration_retry_task` 的 `tenant_id` 改为必填并建立外键；重试任务从消息继承租户。
- 为处方、煎煮任务、物流单、短信记录、标签打印和导出任务补齐 `version`；为物流、回调补齐缺失外键。
- 扩展 `operation_log` 的请求 ID、客户端地址和变更前后快照，支持高风险操作追踪。

### 9.3 V45 业务历史与批量任务

- 新增 `order_address_change_record` 和 `prescription_change_record`，保存变更前后 JSONB 快照、原因、操作人和请求 ID。
- 新增 `import_task`、`import_task_error`，承载文件摘要、总量、成功/失败数量和逐行错误。
- 新增 `sms_batch_task`、`sms_batch_recipient`，区分批次聚合状态与单个接收人发送结果。
- 新增 `print_task`，承载批量打印请求、模板、载荷和结果统计。
- 新增 `shipment_followup_record`，保存未签收跟进状态、联系信息、处理结果和下次跟进时间。

### 9.4 当前边界

V43-V45 只完成数据库基础和 callback/integration 原子认领，不代表管理端登录、令牌签发、菜单接口鉴权、工作流领取接口、导入执行器、短信群发执行器、真实打印或未签收跟进接口已经完成。后续业务代码必须使用这些表，禁止继续以固定租户或前端按钮可见性代替后端鉴权。

## 10. 管理端数据范围强制策略（V46）

V46 将管理端数据隔离从 Repository 自觉约束提升为数据库强制约束：

- 新建无登录能力的 `zhyf_admin_scoped` 数据库角色，只授予应用表的必要 DML 权限。
- 业务服务收到 gateway 注入的管理端上下文后，在请求事务中设置 `zhyf.admin_tenant_id`、`zhyf.admin_tenant_wide`、`zhyf.admin_institution_ids`，并执行 `SET LOCAL ROLE zhyf_admin_scoped`。
- 对迁移执行时所有包含 `tenant_id` 的表启用 `zhyf_admin_data_scope` RLS policy，读写都必须匹配当前租户。
- 机构范围优先使用 `institution_id`；没有直接机构字段时，通过 `order_id`、`prescription_id`、订单业务键、合单明细或集成来源绑定解析机构归属。
- 机构范围角色对无法可靠关联机构的导出、导入、打印、短信批次和集成重试任务默认不可见；租户全域角色不受该机构层限制。
- `message_consume_log`、`dead_letter_record` 补充必填 `tenant_id`、外键和索引；存量数据优先按 `event_outbox.event_id` 回填，无法关联的开发存量归入最早租户。
- 管理端权限字典按业务域和动作初始化，所有内置 `TENANT_ADMIN` 角色获得现有权限，普通角色必须显式建立 `admin_role_permission` 关系。

RLS 只在管理端事务切换到受限角色时生效，消息扫描、服务间内部调用、机构签名接口和兼容协议继续使用原数据库会话。新增含 `tenant_id` 的表时，后续 migration 必须同步建立相同策略，不能假设 V46 的动态扫描会自动覆盖未来表。

## 11. 权限字典名称修正（V47）

V47 不新增表和字段，只修正 V46 初始化的 29 个权限中文名称与资源描述：

- 保持权限编码、角色权限关系和接口鉴权规则不变，现有 JWT 权限编码继续兼容。
- `system:read/system:write` 资源描述补充 `/api/admin/rbac/**`。
- 煎药权限资源描述同时覆盖管理配置与模拟器入口。
- 前端角色编辑器显示权限名称，提交和鉴权始终使用稳定的 `permission_code`。

## 12. 管理端会话与授权变更吊销（V48）

- 新增 `admin_auth_session`，按租户和用户关联 `operator_user`，保存刷新令牌哈希、访问/刷新过期时间、会话状态、吊销原因和版本号。
- 刷新令牌列只允许 64 位 SHA-256 十六进制摘要并建立唯一约束；服务端不保存令牌明文。
- 活跃会话按 `(tenant_id, user_id, refresh_expires_at)` 建部分索引，过期扫描按 `refresh_expires_at` 建索引。
- 该表显式启用 `zhyf_admin_data_scope` 策略，同时撤销 `zhyf_admin_scoped` DML 权限；会话只由认证服务和 gateway 的普通应用连接维护。
- 操作员安全字段、用户角色/机构范围、角色权限/机构范围和角色定义变化通过触发器吊销关联活跃会话，授权变更与业务写入处于同一数据库事务。
- V48 只新增向后兼容结构；旧应用镜像不读取该表，回滚应用时不需要删除表或触发器。

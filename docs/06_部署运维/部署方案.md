# 部署方案

## 1. 部署目标

部署目标是把智能药房 SaaS 平台部署到开发测试云服务器：

```text
47.120.55.53
```

目标要求：

- 前端通过 Nginx 暴露 80/443。
- 后端业务服务容器化部署。
- PostgreSQL、Redis、RocketMQ 和观测组件运行在同一台开发测试服务器。
- Grafana、Prometheus、SkyWalking UI、1Panel 只允许白名单访问。
- 敏感信息只保存在服务器侧 `.env` 或 secrets，不写入仓库。

## 4. 部署目录

推荐：

```text
/opt/zhyf
|-- docker-compose.yml
|-- .env
|-- secrets
|-- nginx
|-- logs
|-- backups
|-- skywalking
|-- prometheus
|-- grafana
```

要求：

- `.env` 不提交仓库。
- `secrets` 不提交仓库。
- 数据库备份放到 `backups` 或独立磁盘。
- RocketMQ 存储目录、NameServer/Broker 配置需要纳入备份范围。
- docker-compose、镜像 tag、Nginx 配置和观测配置需要能在新服务器重建。
- 日志必须配置滚动和大小限制。

## 5. 部署流程

### 5.1 构建前端

```text
cd frontend/admin-web
npm install
npm run build
```

产物复制到 Nginx 静态目录或构建为 `admin-web` 镜像。

### 5.2 构建后端

```text
cd backend
mvn clean package
```

当前后端使用 Spring JDBC，构建时需要确认 Repository、查询 DTO 和 Flyway migration 同步；持久化框架迁移不属于常规发布步骤。

### 5.3 启动顺序

```text
PostgreSQL
Redis
RocketMQ NameServer
RocketMQ Broker
SkyWalking OAP
Prometheus/Grafana/Loki
gateway
auth-institution
order-service
prescription-service
message-service
workflow-service
callback-service
decoction-service
logistics-service
portal-service
report-service
integration-service
ops-service
admin-web/Nginx
```

### 5.4 当前开发服务器发布方式

当前开发服务器保留 `/opt/zhyf/docker-compose.yml` 作为配置归档，但主机未安装 Docker Compose 插件或独立 `docker-compose` 命令，现有应用容器也没有 Compose 标签。因此不能直接执行 `docker compose up`。

当前发布必须遵守：

- 从原容器读取网络、回环端口、挂载、重启策略和环境变量，只替换明确版本的应用镜像。
- 环境变量通过服务器侧权限为 `0600` 的临时文件传入，创建容器后立即删除，不在命令输出或项目文档中打印变量值。
- 先停止并重命名旧容器为带时间戳的 `prev` 容器，再创建同名新容器；健康检查失败时删除新容器并恢复旧容器。
- 包含 Flyway 的发布先启动 `order-service`，确认 migration 版本和健康状态后，再启动依赖新字段的其他服务。
- 每次结构迁移前先执行事务回滚预检和 `pg_dump` 备份。
- 服务端口必须按本方案端口表和原容器配置逐项核对，不得按模块顺序推算；`message-service` 使用 `18083`，`prescription-service` 使用 `18084`。
- 启用 SkyWalking 的应用容器挂载主机 `/opt/zhyf/skywalking/agent` 到容器 `/opt/skywalking/agent`，Agent 目录只读，`/opt/skywalking/agent/logs` 使用独立可写日志挂载；不得依赖旧容器可写层中的 Agent 文件。

后续应安装并固定 Docker Compose 版本，将现有手工容器纳入同一 Compose 项目后，再恢复标准化 `docker compose up -d` 发布。

### 5.5 管理端认证配置

- `auth-institution` 和 `gateway` 必须使用相同的 `ZHYF_ADMIN_JWT_SECRET` 与 `ZHYF_ADMIN_JWT_ISSUER`。
- JWT 密钥不得写入镜像、Compose 归档、Git 或日志；当前开发环境只保存在服务器 `/opt/zhyf/secrets/admin-auth.env`，文件权限为 `0600`。
- 初始管理员的租户、用户名和初始密码也保存在上述服务器文件中；密码修改接口尚未交付前不得把该文件复制到其他位置或放宽权限。
- Nginx 的 `auth/order/workflow/message/decoction/ops/logistics/callback/portal/report/integration` API 前缀统一代理 gateway，不能再直接代理业务服务。
- 后台业务服务端口继续只绑定回环或容器内网，避免绕过 gateway 直接提交伪造身份头。
- gateway 需要配置各下游服务的内部 URL；浏览器提交的 `X-Admin-*` 头不得透传，必须由 gateway 根据已验证令牌覆盖生成。

### 5.6 管理端数据范围发布

- Flyway V46 创建的 `zhyf_admin_scoped` 是 `NOLOGIN` 数据库角色，仅用于请求事务内 `SET LOCAL ROLE`，不得配置为应用连接账号。
- 每次新增带 `tenant_id` 的业务表时，必须同步增加或验证 `zhyf_admin_data_scope` RLS 策略；发布检查中，含租户字段的业务表数量应与该策略数量一致。
- gateway 负责校验权限并覆盖注入用户、租户、机构、权限和 `tenantWide` 可信头；业务服务不得接受绕过 gateway 的公网管理端请求。
- 数据范围过滤器依赖单次请求事务保持 PostgreSQL `set_config(..., true)` 和 `SET LOCAL ROLE` 生效；下游返回 4xx/5xx 时必须回滚该事务，保留原业务错误响应。
- 发布验收至少包含租户管理员、单机构受限角色和匿名请求三组用例，覆盖本机构读写、跨机构读写阻断、无权限接口 403、内部接口 403 以及临时数据清理。

## 6. 验证步骤

基础验证：

- `docker ps` 确认容器运行。
- `http://47.120.55.53/` 能打开前端。
- gateway 健康检查正常。
- 各服务 actuator 健康检查正常。
- PostgreSQL、Redis、RocketMQ 可用。

业务验证：

```text
外部下单 -> 后台订单列表 -> 审方 -> 调剂 -> 复核 -> 煎煮 -> 物流 -> 回调
```

观测验证：

- SkyWalking 能看到服务拓扑。
- Prometheus target 正常。
- Grafana 能查看服务和主机指标。
- 日志能按服务、订单号、操作人和时间窗口查询。

消息可靠性验证：

- 停止 RocketMQ Broker 后，业务服务仍能写入 `event_outbox`。
- RocketMQ 恢复后，`message-service` 能自动补发失败事件。
- 停止一个消费者后，Topic 积压可见，消费者恢复后能追平。
- 重复投递同一事件时，`message_consume_log` 能保证幂等。
- 死信或失败消息能在运维后台查询并人工重放。

## 7. 回滚策略

- 前端保留上一版镜像或静态目录。
- 后端镜像使用明确版本 tag。
- 数据库上线前备份。
- Flyway migration 不直接删除，错误变更通过补偿 migration 修复。
- 发现严重问题时先回滚 Nginx/gateway 路由或后端镜像。

## 8. 容灾恢复

容灾专项方案见：

```text
docs/中间件说明/RocketMQ可靠性与容灾方案.md
```

第一版开发测试环境按单机容灾设计：

- PostgreSQL 每天定时备份，升级前手动备份。
- RocketMQ 故障后优先从 `event_outbox` 补发核心业务事件。
- Redis 不作为唯一事实源，缓存可从数据库重建。
- 整机不可用时，先恢复数据库，再恢复 Redis/RocketMQ，再启动应用服务。
- 恢复后必须执行 Outbox 对账、消费日志检查、死信检查和订单主链路验证。

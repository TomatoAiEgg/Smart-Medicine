# 阶段验收清单

## 1. 验收原则

每个阶段完成后必须验收，不能只看“代码写完了”。验收要覆盖：

- 文件范围是否正确。
- 构建和静态检查是否通过。
- 数据库、API、MQ、状态机契约是否一致。
- 核心业务链路是否能跑通。
- 异常、幂等、重试、补偿是否可验证。
- 监控、日志、链路追踪是否能定位问题。
- 是否有敏感信息泄露。

阶段验收由主控窗口负责。worker 或 explorer 可以提供结果，但最终是否通过由主控判断。

## 2. 通用验收动作

每个阶段都先执行：

```text
git status --short
git diff --check
```

检查项：

| 检查项 | 通过标准 |
| --- | --- |
| 改动范围 | 只修改本阶段授权范围 |
| 敏感信息 | 无密码、token、密钥、真实患者信息 |
| 格式 | `git diff --check` 无错误 |
| 文档 | 关键契约变更有同步说明 |
| 验证 | 有可复现命令和结果 |
| 回滚 | 能说明失败后如何回退或补偿 |

敏感信息检查建议：

```text
rg -n "password|passwd|pwd|secret|token|appSecret|accessKey|privateKey|身份证|手机号" .
```

命中后必须人工判断，不能把真实密钥或真实患者信息提交。

## 3. 第一阶段：只读审查验收

目标：

```text
多 explorer 完成后端、前端、数据/MQ、监控压测只读审查。
```

验收输入：

- 后端 explorer 审查结果。
- 前端 explorer 审查结果。
- 数据/MQ explorer 审查结果。
- 监控压测 explorer 审查结果。

通过标准：

| 类别 | 通过标准 |
| --- | --- |
| 后端 | 说清楚订单创建、审方、调剂、复核、Outbox、MQ、事务缺口 |
| 前端 | 说清楚老前端核心功能和新前端页面差异 |
| 数据/MQ | 说清楚核心表、索引、Outbox、消费日志、死信和容灾缺口 |
| 监控压测 | 说清楚链路追踪、SQL、MQ、压测、故障演练缺口 |
| 修改文件 | explorer 不应修改任何文件 |
| 输出质量 | 每个结论有文件、代码、配置或文档依据 |

主控产出：

```text
公共契约草案
阶段二执行顺序
风险清单
```

## 4. 第二阶段：公共契约验收

目标：

```text
统一数据库、API、状态机、MQ 事件、Outbox、消费日志和前后端联调契约。
```

验收范围：

- 数据库 migration 或数据设计文档。
- API DTO / OpenAPI / 前后端联调文档。
- 状态机枚举和状态文案。
- RocketMQ Topic、事件、消费组。
- Outbox、消费日志、死信字段。

通过标准：

| 契约 | 通过标准 |
| --- | --- |
| 数据库 | 表、字段、索引、唯一约束、状态字段清楚 |
| API | 前端需要的字段、分页、筛选、错误码清楚 |
| 状态机 | 每个状态能说明来源、下一状态、失败处理 |
| MQ | Topic、eventType、payload、consumerGroup 清楚 |
| Outbox | 状态机包含 `NEW/PUBLISHING/PUBLISHED/PUBLISH_FAILED/WAIT_CONSUME_TIMEOUT/DEAD` |
| 消费日志 | `consumer_group + event_id` 幂等约束清楚 |
| 文档一致 | 架构、数据、功能、联调文档没有互相冲突 |

建议命令：

```text
rg -n "event_outbox|message_consume_log|dead_letter|WAIT_CONSUME_TIMEOUT|OrderCreated|PrescriptionReviewed" docs
rg -n "JDBC|jdbc|trace_id|traceId|老笔记本|Tailscale|100\.115" docs
```

第二条命令应无不合理命中。

## 5. 第三阶段：数据和中间件验收

目标：

```text
数据库、Redis、RocketMQ、Docker/Nginx 基础配置可用。
```

通过标准：

| 项 | 通过标准 |
| --- | --- |
| PostgreSQL | migration 可执行，核心表存在 |
| 索引 | 订单号、租户、状态、时间、处方号有必要索引 |
| Redis | key 规范明确，不保存唯一业务事实 |
| RocketMQ | Topic 和 ConsumerGroup 规划明确 |
| Outbox | 支持发布失败重试和超时释放 |
| 消费日志 | 支持幂等和失败原因记录 |
| 死信 | 支持查询、重放、关闭 |
| Docker | `docker compose config` 可通过 |
| Nginx | 前端和 gateway 路由清楚 |

建议命令：

```text
docker compose config
mvn -q -DskipTests package
```

如果当前阶段只做文档或 migration 草案，必须说明没有执行部署验证的原因。

## 6. 第四阶段：后端核心链路验收

目标：

```text
外部下单 -> 订单落库 -> 处方明细 -> Outbox -> MQ -> 审方 -> 调剂 -> 复核 -> 回调事件。
```

通过标准：

| 链路 | 通过标准 |
| --- | --- |
| 订单创建 | 订单、处方、明细、状态日志、Outbox 同事务成功 |
| 幂等 | 重复外部订单不会生成重复订单 |
| 审方 | 并发审方只有一次成功 |
| 调剂 | 重复调剂不会重复推进状态 |
| 复核 | 复核完成后生成后续事件 |
| MQ | 消费失败有日志，可重试或进死信 |
| 事务 | 外部 HTTP 不在数据库事务里 |
| 错误处理 | 错误码、失败原因、操作日志完整 |
| 构建 | 后端构建或测试通过 |

建议命令：

```text
mvn test
mvn clean package
```

接口验收用例：

```text
创建订单
重复创建同一外部订单
两个操作员同时审方
重复点击调剂
重复点击复核
模拟 MQ 消费失败
人工重放失败事件
```

## 7. 第五阶段：前端业务页面验收

目标：

```text
后台人员能完成工作台查看、订单查询、审核、调剂、复核、物流和运维补偿操作。
```

通过标准：

| 页面 | 通过标准 |
| --- | --- |
| 工作台 | 展示待审方、待调剂、待复核、回调失败、Outbox 积压 |
| 订单中心 | 支持分页、筛选、详情、状态展示 |
| 审核任务 | 能查看处方并提交审方结果 |
| 调剂任务 | 能完成调剂并看到状态变化 |
| 复核任务 | 能完成复核并触发后续状态 |
| 物流发货 | 能查看待发货和发货结果 |
| 运维审计 | 能查看失败消息、死信、补偿入口 |
| 交互 | 重复点击有防抖或服务端幂等提示 |
| 响应式 | 常见桌面宽度不遮挡、不溢出 |

建议命令：

```text
npm run type-check
npm run build
```

如果没有类型检查脚本，至少运行项目已有的 lint/build 命令。

## 8. 第六阶段：前后端联调验收

目标：

```text
前端页面通过真实后端接口完成核心业务闭环。
```

通过标准：

| 项 | 通过标准 |
| --- | --- |
| 登录 | 能获取并携带认证信息 |
| 列表 | 分页、筛选、状态文案正确 |
| 详情 | 订单、处方、状态日志展示完整 |
| 操作 | 审方、调剂、复核能推进状态 |
| 错误 | 后端错误能转成可读提示 |
| 幂等 | 重复操作不会造成重复状态 |
| 日志 | 后端能按订单号、操作人、事件 ID 查日志 |
| 链路 | SkyWalking 能看到接口调用链 |

联调用例：

```text
登录后台
创建测试订单
刷新工作台数量
进入订单详情
完成审方
完成调剂
完成复核
查看 Outbox/MQ 消费记录
查看回调或补偿记录
```

## 9. 第七阶段：监控和链路追踪验收

目标：

```text
服务、接口、SQL、MQ、日志、业务链路可观测。
```

通过标准：

| 监控项 | 通过标准 |
| --- | --- |
| 服务健康 | actuator health 可用 |
| Prometheus | target 正常 |
| Grafana | 有服务、JVM、HTTP、DB、MQ、业务指标看板 |
| SkyWalking | 能看到 gateway 到各服务链路 |
| SQL | 能定位慢 SQL、连接池、锁等待 |
| MQ | 能看到 Outbox、积压、消费失败、死信 |
| 日志 | 能按订单号、处方号、事件 ID 查询 |
| 告警 | 核心阈值有明确告警规则 |

故障验证：

```text
调用一个慢查询接口
制造一次消费失败
停止 callback-service 5 分钟
查看 SkyWalking、Grafana、日志和补偿记录
```

## 10. 第八阶段：压测和故障演练验收

目标：

```text
通过模拟压测获得真实可讲的容量验证和高并发治理经验。
```

通过标准：

| 档位 | 通过标准 |
| --- | --- |
| 20 并发 | 全链路稳定，无核心 5xx |
| 50 并发 | 核心接口错误率低于 1% |
| 100 并发 | 允许短暂 MQ 积压，压测后能追平 |
| 200 并发 | 用于找瓶颈，不承诺稳定 |

必须记录：

```text
压测日期
代码版本
环境
并发档位
持续时间
订单数量
P95/P99
错误率
MQ 最大积压
追平时间
慢 SQL
瓶颈
优化动作
复测结果
```

故障演练：

```text
停止 RocketMQ Broker 5 分钟
停止 workflow-service 5 分钟
重复投递同一 MQ 消息
重复提交同一订单
两个窗口同时审方
删除 Redis 缓存后重建
恢复 PostgreSQL 备份
```

## 11. 第九阶段：部署验收

目标：

```text
开发测试服务器能稳定部署和回滚。
```

通过标准：

| 项 | 通过标准 |
| --- | --- |
| 容器 | `docker ps` 关键容器正常 |
| 前端 | `http://47.120.55.53/` 能打开后台 |
| gateway | 健康检查正常 |
| 中间件 | PostgreSQL、Redis、RocketMQ 可用 |
| 观测 | SkyWalking、Prometheus、Grafana 可用 |
| 安全 | 中间件端口不直接公网暴露或有白名单 |
| 配置 | `.env` 和 secrets 不入仓库 |
| 备份 | PostgreSQL 和关键配置有备份路径 |
| 回滚 | 前后端镜像和数据库 migration 有回滚或补偿策略 |

部署后业务验证：

```text
外部下单 -> 后台订单列表 -> 审方 -> 调剂 -> 复核 -> 煎煮 -> 物流 -> 回调
```

## 13. 不通过处理

不通过时不进入下一阶段。

处理流程：

```text
定位失败项
 -> 判断是契约问题、实现问题、环境问题还是测试数据问题
 -> 分派给对应 worker 修复
 -> 主控复验
 -> 记录原因和修复结果
```

常见阻断项：

- 后端构建失败。
- 前端构建失败。
- migration 无法执行。
- 外部下单无法落库。
- 审方、调剂、复核状态无法闭环。
- MQ 消息发出但无法消费。
- 重复提交导致重复订单或重复任务。
- 死信无法查询或重放。
- 监控无法定位错误。
- 部署环境缺少恢复路径。

## 14. 当前项目建议

本项目阶段验收重点不是追求一次性做大，而是每一阶段都留下可验证证据：

```text
能构建
能启动
能联调
能追踪
能压测
能补偿
能恢复
```

每次多智能体 worker 完成后，都必须先过本清单，再进入下一轮任务。
